# CLAUDE.md

Personal budgeting app: Create React App at the repo root, **one household per account**, backed by Supabase (Postgres + Auth) with **no server of our own** — and, over the same bundle, an Electron desktop app whose books are a file the household owns. Every store persists through `useSyncedState` (`src/hooks/useSyncedState.js`) — `useState`-shaped, JSON, optional third `migrate` arg applied to stored values but never to the default.

## Commands

Run from the repo root.

- `npm start` — dev server at http://localhost:3000
- `npm test` — Jest + RTL, watch mode. Single file: `npm test -- --watchAll=false src/App.test.js`
- `npm run build` — production build
- `npm run desktop` — the shell against the dev server, hot reload and all
- `npm run desktop:build` — packaged into `dist/win-unpacked` (etc.), no installer
- `npm run desktop:dist` — the installer for the platform you are on
- `npm run shell-config` — regenerate `electron/shell-config.json` alone; the three above already do

No lint script; CRA's ESLint (`react-app`) runs during `npm start` / `npm test`.

Credentials live in `.env.local` (gitignored; copy `.env.example`). `supabase/schema.sql` is the whole server side and is idempotent — paste it into a new project's SQL editor.

`node buildResources/makeIcon.js` redraws the app's icon — the packager's copy and the web build's favicons — from the palette. The output is committed; run it when a colour moves.

## Accounts, and why they exist

The app was single-user with no auth for its whole life. What ended that is not a second person: it is that **the books moved off the browser**. A Supabase anon key is compiled into the JavaScript bundle and is public by design, so the only thing between a household's ledger and anyone who opens devtools on the deployed app is a row-level-security predicate — and a predicate needs a subject. `auth.uid()` is that subject, which is what makes an account load-bearing rather than a feature.

**One table on the server**, `app_state (user_id, key, value jsonb, updated_at)`: one row per store, the whole value as a document. Not a relational split, because every derivation here loads a whole array and computes over it in JS — so a split buys nothing and costs the synchronous `{ ok, error }` contract that ~40 call sites and the invariant tripwires depend on. One table is also one policy pair to get right instead of fifty.

**Four layers wrap `AppProviders` in `index.js`, in the order the questions have to be answered:**

- **`AuthProvider`** (`src/contexts/AuthContext.js`) — the session and what you can do about it. Mutators return `{ ok, error }` like every store, wrapped in a promise. `status` is a **three-state, not a boolean**: "checking" is real, because a persisted session is read back asynchronously and a gate that read the gap as signed-out would flash the sign-in form at every returning user on every reload. `describeAuthError` is the one place an API string becomes a sentence, so two forms cannot word the same failure differently.
- **`AuthGate`** (`src/components/AuthGate.js`) — **recovery is checked before the session**, because a reset link *signs you in* (that is how the change is authorised) and checking the session first would drop someone who clicked "I forgot my password" onto the dashboard and never ask for a new one.
- **`SyncProvider`** (`src/contexts/SyncContext.js`) — fetches the account's documents in one query, writes them into the local cache, and **holds the render until they are there**. Documents are compared through **`canonicalJSON`** (keys sorted), never a bare `JSON.stringify`: Postgres `jsonb` reorders keys, so a plain comparison read every realtime echo of our own write as another device's change, re-applied and re-pushed it, and kept "Saving…" lit forever. The header's sync badge reserves its widest label's width so it cannot reflow the controls beside it. This gate is the load-bearing piece of the whole design: three store initialisers (`foldLegacyLedger`, `readStoredLedger`, `legacyPlannedCentsById`/`storedGroupBuckets`) read storage **synchronously** to build their lazy defaults and run before the first paint. Gating the render is what let every migration, every mutator and every tripwire survive the move to Postgres untouched. It also coalesces writes (one round trip per burst of blur-commits, not one per column), keeps a failed push queued rather than dropping it, and subscribes to realtime — which is the `storage` event's job one device wider, since every write replaces a whole document.
- **`ImportBooksGate`** (`src/components/ImportBooksGate.js`) — the one-time offer to carry this browser's pre-account books into an empty account. Offered on **two** conditions, and the second is what makes it safe: this browser holds books *and* the account is still empty, so there is nothing to overwrite. Legacy keys travel too, or a browser that never ran the current build carries up an empty account.

**There are two ways in, and the second is not a convenience.** A password is the original route. An emailed credential is the other, and it is here because the project behind these accounts is no longer this app's alone: it also serves another app that signs people in by link, by code and through Google and GitHub, and every one of those routes writes a row in `auth.users` with `encrypted_password` **null**. Such a household has a perfectly good account here and, before this, no way to reach it — `signInWithPassword` answers "invalid login credentials", which the form words as a password that does not match when the truth is that there is no password to match, and password *recovery* was the only way through, which is a strange thing to ask of somebody who never had one. `requestSignInEmail` is that route, and **`shouldCreateUser` is false on it, which is the load-bearing choice**: left at its default this would quietly become a second way to register — one that mints exactly the passwordless account it was written to rescue, and does it for a typo'd address as readily as a real one. An account is created by the sign-up form, which asks for a password and confirms it; this reaches accounts that already exist. Which means an unknown address is refused **by name** (`otp_disabled`), and reporting that refusal would turn the form into a way to test whether a given household keeps their books here — so `isUnknownAccountError` is asked only so the answer can be thrown away: the call reports success either way and the page says "if an account exists", which is true in both cases and distinguishable in neither. It is the same leak the reset form is already worded around.

**One call, two shapes of email, and this is the one place the two builds are offered different *mechanics* rather than different wording.** The browser sends `emailRedirectTo` and follows the link back to its own origin. The shell is served over `app://`, which no mail client and no OS browser can open, so it sends **no** redirect at all — and deliberately not the `app://` origin either, because an un-allow-listed redirect does not fail the request, it falls back to the project's Site URL, and that URL now belongs to whichever of the two apps claimed it, so asking for a link we cannot receive risks sending a household into the *other* app. Saying nothing is the honest version of "the link is not the part you want". The shell reads the six-digit token out of the same email instead, through `verifySignInCode`, under **`type: "email"` and never `"magiclink"`** — both halves are rendered by the project's single Magic Link template, which is why that template has to carry `{{ .Token }}` beside `{{ .ConfirmationURL }}` (see `supabase/schema.sql`'s header, since this is a dashboard setting no SQL can state), but the token in it is an email OTP and verifying it under the link's type is refused. `MAGIC_CODE_LENGTH` is what the copy **says** — six, the project's default — while `checkCode` accepts six to ten digits, because the length is a dashboard setting and insisting on today's value here would turn raising it into a form that refuses every real code. The server is the one that knows; this only catches what obviously is not a code at all.

**`pendingSignInEmail` is half of the credential, not a flag.** `verifyOtp` needs the address as well as the code and only the code was typed, so taking the address from anywhere else would let a code be verified against an address it was never sent to. It is cleared **the moment a session exists**, not when the form is left: this provider outlives `AuthPage`, which unmounts as soon as there is a session and mounts again on the next sign-out, so an address left lying here would greet that sign-out with "check your inbox" for an email sent before the session that has just ended. One sentence covers every way an emailed credential can fail — lapsed, mistyped, or a link followed twice — because a person cannot act on the difference and all three are fixed by asking for another.

**On `AuthPage` this is a second button under the sign-in form, not a mode.** It needs exactly one field and that field is already on the form, so a screen of its own would ask again for the address just typed; the password field sitting above it unused is the honest shape of the choice. It is a `type="button"` so Enter cannot trigger it, and offered on **sign-in only** — there is nothing to email somebody who is registering, and the reset form is already an emailed route. The screen that waits on the email is a fifth state for the recovery form's reason: it is arrived at rather than chosen. Its code field is `type="text"` with `inputMode="numeric"` and `autoComplete="one-time-code"` — the app's no-`type="number"` rule holding for its own reason here, since a code can begin with a zero and is pasted at least as often as it is typed.

**`localStorage` is now a cache with a synchronous read, not the source of truth** — and `src/storage.js` is the only module that knows the shape of a key. Keys are **namespaced by user** (`hb:<uid>:<key>`), and `scopedKey` returns the **bare key when nothing is in scope**. That unscoped mode is not a degenerate path, it is the app's other supported one: an unconfigured build (no `.env.local`) runs signed out on this browser's own books, which is exactly how the whole test suite runs, and the books written before accounts existed *are* the unscoped documents. **Adding a store means adding its key to `STORE_KEYS`** or it lives in the browser and never reaches the server — `storage.test.js` reads the contexts and fails if you forget. Sign-out calls `clearScope`, which is the reason for namespacing at all: the books have to leave the browser with the session.

## The desktop shell

Accounts answered "how do two devices share one household's books". The desktop build answers the question underneath it, which the web build cannot: **a household that wants their ledger on their own machine and nowhere else.** A browser cannot honour that promise — `localStorage` is cleared by anything that clears a cache, it does not survive the machine, and "on this computer" in a tab is a much smaller claim than the same words beside a file on disk. So the shell is not a wrapper around the web app for convenience; it is the build where local mode is actually true, and every line in `electron/` is either the machinery that makes it true or the machinery that keeps it true when somebody does sign in.

**Three files, and one rule each.** `electron/main.js` is the process and the promise; `electron/books.js` is the file; `electron/preload.js` is the entire surface the page can reach. The renderer stays sandboxed with no Node integration, so the bridge is a snapshot plus four verbs and deliberately nothing general — no "read a file", no "run a command".

- **The app is served over `app://`, registered as standard *and* secure**, never `file://`. A standard scheme gets a real origin, so the History API works (`BrowserRouter` and every deep link keep working untouched) and `localStorage` and a normal CSP behave exactly as they do on https; under `file://` all three break at once. A path with no extension is a route and falls back to `index.html`, which is the same single-page rewrite the web deploy relies on — and it is why `homepage` stays unset in `package.json`, since setting it to `"./"` would have broken deep links on the web to fix them here.
- **Egress is an allow-list, not a deny-list**, plus Chromium's own background networking switched off by name. The requirement is "zero requests", and a deny-list can only block what somebody thought of. What is allowed is the app's own origin and — only when the build has one — the account server. **Development is "pointed at a dev server", not "not packaged"**: keyed off `ELECTRON_START_URL` rather than `app.isPackaged`, because every relaxation (`unsafe-eval`, localhost in the filter) exists for CRA's dev server, and `electron .` against `build/` should exercise exactly the path a packaged app takes.
- **The policy is one policy written in three languages** — `vercel.json` for the web deploy, `contentSecurityPolicy()` for the shell, and the egress filter beside it. Nothing can share a string between a JSON file Vercel reads at deploy time and JavaScript Electron reads at run time, so **changing one means changing the others**.
- **The one host it may open is resolved at build time, by `electron/writeShellConfig.js`, and never from `process.env`.** CRA inlines `REACT_APP_SUPABASE_URL` into the bundle; nothing puts it into the environment of the Electron process spawned beside the dev server, and a packaged app launched from a dock has no developer shell behind it at all. Read from the environment it was `null` in every real run — the filter cancelled every request to the account server and sign-in failed with the form saying nothing. The generator reads the same `.env` files CRA does, in CRA's own order, and writes `electron/shell-config.json` (gitignored, shipped inside the package). It **always writes, including a `null`**: a stale file would let the shell open a host the bundle beside it knows nothing about, which is the one failure an allow-list exists to prevent.
- **The window's cold-start colour is a fourth copy of the palette, hard-coded.** `groundColor()` in `main.js` opens the `BrowserWindow` on `ledger`'s value for the mode, because the main process cannot read a CSS variable — so the two `--c-ledger` figures in `index.css` have a copy there, and `index.html`'s `theme-color` is a third (the header's green rather than the page's ground). It reads `nativeTheme`, not the stored choice: the preference lives in the renderer's `localStorage`, which does not exist until there is a renderer, and this figure is needed to build one. Somebody who pins a mode *against* their OS therefore gets one frame of the other ground — closing that would mean main keeping a second copy of a fact the renderer owns, which is the worse trade.
- **One window and one instance.** Two processes over one file is last-writer-wins with no warning and no trace; the cross-tab `storage` event was the guard against that shape of loss one process narrower, and nothing plays that role here.

**`electron/books.js` holds the books in the main process, and the placement is load-bearing twice.** The renderer needs a **synchronous** read at start-up — five things read storage before the first paint, the four store initialisers plus `isGuestMode()` above every gate — and `sendSync` can only be answered by a process that already has the data, which is why `load()` runs before the window is created. And **the debounce has to survive the renderer**: a timer in the page cannot be flushed from `before-quit`, because by then the page is gone. So the renderer posts every write across immediately and the coalescing happens in main, where the quit handlers can reach it. `books:readAll` is answered by `ipcMain.on` setting `event.returnValue` — **never `ipcMain.handle`**, which returns a promise that `sendSync` reads as `undefined`, and the app would boot silently with empty books.

Four durability rules, all of them because in local mode this file is the only copy of the books anywhere:

- **Temp file, then rename.** A rename within a directory is atomic, so a crash or a pulled plug leaves either the old file or the new one and never half of either.
- **A trailing debounce (300ms) *and* a cap counted from the first dirty write (2000ms).** Without the cap the trailing timer is starved indefinitely — tabbing across a row of the register commits a cell every couple of hundred milliseconds and nothing ever reaches the disk. Deliberately not `SyncContext`'s 700ms, which is tuned for a network round trip.
- **The backup is the file as it was found at launch, taken lazily at the first write, once.** Temp-and-rename already makes a torn write impossible, so a copy from three hundred milliseconds ago protects against nothing; what a person wants back is "the books as of last time I opened the app", and for that the copy has to be old.
- **A file that will not parse is moved aside, never overwritten.** Starting empty and saving over it would destroy the only copy at the exact moment something had already gone wrong with it. A failed write keeps the books dirty, so the next write or the next quit tries again.

The documents are stored **parsed** and re-serialised per read at the renderer's end, which is the split that lets the same file be both a drop-in `Storage` and something a person can open in a text editor.

**`src/desktop.js` is the only module that knows the bridge's shape**, the discipline `storage.js` keeps for the shape of a key, and **every function in it is safe to call in a browser** — `isDesktop` is false, there is no path, and the rest are no-ops that report they did nothing, which is what keeps callers free of `if (isDesktop())` around every use. `deviceLabel()` is the one place the app decides whether to call the machine a computer or a browser; where the two readings differ by more than the noun ("safe *on* this computer" against "safe *in* this browser") the caller writes both sentences out. In `storage.js` the medium is one seam lower, in `webBackend` / `desktopBackend` — the same three methods `localStorage` has, over strings. **The desktop backend reads from memory, never from disk**, seeded from the preload's snapshot, which is the whole reason that seam can exist at all.

**Local mode is unscoped in the shell and `GUEST_SCOPE` in a browser**, and the asymmetry is the point: there the bare keys *are* the household's real books, since the file belongs to one machine and there is nobody to collide with, while in a browser the unscoped documents are *this browser's* pre-account books and a stranger trying the app out on a shared machine must not type into them. `AUTH_STATUS.GUEST` is a fact about the **person** (offered an account, declined for now, so the app owes them a way back) where `LOCAL_ONLY` is a fact about the **build** (nothing configured, so there was never an account to decline). `stopSyncing` is the counterpart to `signOut` and not a variant of it: signing out is destructive on purpose, because on a shared browser the books must leave with the session, but on a machine somebody owns that answers "I would rather my ledger were not on a server" by deleting the ledger.

**`src/booksFile.js` is the books as a file and back**, one serialiser for the export, the archive before a restore, and the archive before "stop syncing" — a second one would eventually disagree about the envelope, and the file that matters least on the day it is written is the one that matters most a year later. `schema` is in the envelope from the first version rather than added when first needed, because by then every file in the wild lacks it. Parsing is **liberal about the wrapper, strict about the contents** (a bare flat map is accepted; an unknown key is refused rather than dropped, since silently importing the part we understood would leave the user believing they had restored everything) — and `electron/books.js` asks the same question the same way on the way in, so the two readers cannot disagree about one file. `offerFile` is the one door: a save dialog in the shell, a download in a browser, and **cancelling is reported apart from failing**, because dismissing a dialog is an answer and it has to stop the operation it was protecting.

### Packaging

`electron-builder`, configured in package.json's `build` block. Four things there are not obvious and each one cost a broken package to find:

- **`"extends": null` is required.** electron-builder auto-detects `react-scripts` in `dependencies` and applies its `react-cra` preset, which repoints `main` at `build/electron.js` — a file this layout does not have, so the package builds and then fails its own sanity check.
- **`directories.buildResources` must not be `build`**, which is its default and is CRA's output directory. It is `buildResources/`, which is also where the generated `icon.png` lives.
- **`files` excludes `node_modules` outright.** Every runtime dependency here is React and friends, which the static bundle in `build/` already contains, and `main.js` needs nothing but Electron's own built-ins. Including them is a hundred megabytes of installer that never gets loaded; the packaged `app.asar` is under six.
- **`productName` is top-level in package.json, not only inside `build`.** Electron's `app.getName()` prefers it, and `app.getPath("userData")` is built from that — so a name stated only to the packager would put the dev shell's books and the installed app's books in two different folders.

## Money and dates

- **Money is an integer number of cents**, always in a `…Cents` field. Never floating-point dollars. Parse input with `toCents` and render with `formatCents` (`src/utils.js`); `toCents` returns `null` for junk, which is how contexts reject bad input instead of writing `NaN`.
- **`toCents` takes a figure written the way figures are written** — "$1,234.56", "1 234.50", a leading sign — because that is how people type money and it is what `formatCents` itself writes, so a field can show its figure as money and hand it straight back. Never reach for `parseFloat`: it reads "1,234.56" as **1**, stopping at the comma and reporting success. Tolerating the punctuation is not tolerating junk — once the symbol, separators and spaces come off, what is left has to be a number and nothing else, so "12 apples" is `null` where `parseFloat` says 12.
- **Rates are an integer number of basis points**, always in a `…Bps` field — same discipline, same reason. `toBps` / `fromBps` / `formatBps` (`src/utils.js`), and `toBps` returns `null` for junk exactly as `toCents` does — and takes a "%" the same way `toCents` takes a "$". A rate stored as `0.025` is a float the retirement projection raises to the power of thirty, so the drift compounds along with the money.
- **Transactions carry a `date`** (`"YYYY-MM-DD"`, local calendar via `todayISO` — never `toISOString`, which is UTC). Periods (`"YYYY-MM"`) are always **derived** with `toPeriod`, never stored, so the two cannot disagree. Legacy records have `date: null` and display as "Undated"; do not backfill invented history.
- **Compare periods with `periodLTE`, never a bare `<=`** — `null <= null` is `true` in JS, which sweeps undated records into sums that already count them. Step months with `addMonths`, never string arithmetic (`"2026-13"` sorts before `"2027-01"`).
- Migrations live next to the store owning the key and are keyed on **field presence** (`"amount" in record`), not a version counter, so they are safe to re-run.

## Routing

`react-router-dom` v6, pinned: v7's `react-router/dom` export cannot be resolved by the Jest resolver in react-scripts 5. Both routers take the shared `routerFuture` flags (`src/routerFuture.js`).

`src/navigation.js` is the single source of truth for pages, feeding both the route table in `App.js` and the tab bar in `AppShell.js` — **adding a page means adding one entry there**. `src/App.js` is only shell; each page owns its state and modals.

Implemented: `/` (dashboard — today's date, this month's headline figures, accounts with their last reconciliation, categories grouped as the plan groups them, and the one door to moving money between two envelopes), `/transactions` (the editable register, a slim to-be-assigned bar, one ledger-entry modal for money in and out, the split editor, assignment), `/plan` (categories, their estimates and their optional goals, expected income sources, pay schedule, accounts with their opening balances and running totals, the emergency fund measured against the essentials estimates, and — closed, at the foot — the balance-history grid), `/net-worth` (hero figure and band split, twelve-month stacked chart with a table twin, holdings by band with the door to settling a statement against the books, the monthly update pass). `/retirement` (the outlook — what has to be there against what is on course to be — the year-by-year chart with a table twin, the account picker, and the assumptions). `/reports` (the window — five presets or a start and end month of your own — its headline figures and bucket split, the month-by-month cashflow chart with a table twin, the same months drawn against the plan's standing estimate with a table twin of their own, spending by category ranked, and a drill-in on any one of them — its own month-by-month chart with a three-month trend across it, and the exact transactions behind the figure). `/donations` (a year of giving: what was given against what can be claimed, the year's gifts with the organization and the deductible part editable on the row, the goal, and the organizations). `/savings-goals` (the medium-term goals — a camera, a wedding, a special event — each with what it is saving towards, what has accumulated toward it, what is left, and what they are worth, the built-in catalog's value per point beside the household's own, and planned trips — whether each is covered, counting bank-point transfers, and what each point earns on it). `/net-worth` still carries a `Placeholder` for asset allocation, `/retirement` one for scenarios, `/reports` one listing what is still to come there — a recurring filter, CSV export — `/donations` one for non-cash gifts, a year against the years before it, pledges, and CSV export, and `/savings-goals` one for linking a goal to the category or account it draws from, which is the one thing a goal still does not name.

**The dashboard has no period selector.** It answers "where am I right now" and everything on it is as of `todayISO()`, read once in the page so the date, the countdown and the reconciliation ages cannot disagree. Walking back through the books is the Transactions page's job.

**The two pages cut the same books along different axes, and neither repeats the other.** What each *envelope* holds is a question about the plan, and it is answered once, on the dashboard, by `CategoryLedgerTable`. What actually *happened*, line by line, is the register on `/transactions`. The one envelope figure that survives on the register is what is left to assign — it moves as the ledger is worked through, and the flow it opens has nowhere else to be reached from. A grid of envelope cards on `/transactions` was the old shape of that page; do not put one back.

## State: sixteen providers in `src/contexts/AppProviders.js`

Add stores there, not in `index.js`. IDs are generated with `uuid` v4 **in the context**, never in form components.

**Provider order is a cascade order** — a store that has to clean up after another's delete sits *outside* it. `TransactionsProvider` and `AssignmentsProvider` wrap `BudgetsProvider` so deleting a category takes its spend and its funding with it; `TransactionsProvider` also wraps `AccountsProvider` so deleting an account can cut its transactions loose; `DonationsProvider` wraps `TransactionsProvider` so deleting an outflow takes the statement that it was a gift with it; and `SavingsGoalAssignmentsProvider` wraps `SavingsGoalsProvider` so deleting a goal drops every assignment ever made to it; and `TransactionsProvider` wraps `PayeesProvider`, the Accounts relationship again — deleting a payee detaches the rows that named it and merging two repoints them, and both are writes only the ledger can make — the Transactions-outside-Budgets rule again, applied to the one pair that has no catch-all. A deleted category's funding *moves*, to `UNCATEGORIZED_BUDGET_ID`, because there is somewhere for it to land; a deleted goal's simply stops existing, and the money it was holding reappears in "to be assigned", which is exactly where a dollar with nowhere left to go belongs. Each references the other by id and never reads it back — keep the dependency one-way. **Cross-store maths belongs in a hook, never in a provider** (`useEnvelopes`, `useAccountBalances`, `useGiving`, `useSavingsGoalEnvelopes`). `UNCATEGORIZED_BUDGET_ID` lives in `src/contexts/constants.js` for that reason.

- **`TransactionsContext`** — `transactions`: **one ledger for every movement of money**, discriminated by `kind` (`TRANSACTION_KINDS.INFLOW` / `OUTFLOW` / `TRANSFER`), never a signed amount. `amountCents` is a non-negative magnitude. **An outflow must name a `budgetId`; an inflow may.** An inflow with no category is income and lands in the pool; an inflow *with* one is a **refund** against that category — a friend's half of dinner, a returned jacket — which goes back into that envelope and never reaches the pool, because the money was already assigned on its way out. Spend $100 on food and be paid back $60 and food shows $40 of activity. `""` from an unpicked select is normalised to `null` at the boundary. **`payeeId` names who the money went to and `description` is the note beside it** — one free-text field until payees became records, which is the shape a payee cannot be corrected, counted or reasoned about in. It is nullable and **no rule requires it**: this store is mounted *above* `PayeesContext` so it cannot check that a payee exists (the transfer matrix's reason), and a cash withdrawal, a transfer and every record written before the field existed all name nobody. `migrateTransactions` stamps `payeeId: null`, purely additive like `toAccountId` and `splits`; **nothing is minted out of the text a legacy row already holds**, which stays where it is as that row's note. `detachPayeeTransactions` and `repointPayeeTransactions` are the two cascades `PayeesContext` calls — the first `detachAccountTransactions` one field over, the second what a merge is made of. **Every new record must name an `accountId`** — refused at the boundary, so the ledger cannot grow half-finished rows. `accountId: null` and the Uncategorized sentinel still *read* fine (legacy records, and the delete cascade), they just cannot be written. Every rule a record has to satisfy is written out once, as the `RULES` list, and checked through `firstBroken` — because two callers check the same rules against different amounts of the record. `addTransaction` builds a whole one and checks all of it. **`updateTransaction` takes a patch and checks only the rules the named fields could break**, which is what lets the register commit one cell at a time and a legacy row — no date, no account — have its description fixed without being asked to invent the rest. It still cannot *open* one of those gaps: clearing a date or an account touches that field, so the rule runs and refuses. The cross-field rules are "an outflow names a category" and, for a transfer, "names a second account, and a different one" — each lists every field it reads so either side moving re-checks it. A patch that changes nothing is not written, so tabbing across a row does not re-render every consumer once per column. `reassignBudgetTransactions` moves **both kinds**, so a delete cannot strand a refund away from the spend it offsets. `getBudgetTransactions` returns both kinds for the same reason. The lazy default folds the old `income` and `expenses` keys in via `foldLegacyLedger`; the old keys are left in storage. `readStoredLedger` is the no-React read for `AssignmentsContext`'s lazy default. `deleteTransaction` also calls `removeDonation`: a donation record is a statement *about* an outflow and holds no money, so once the outflow is gone there is nothing left for it to describe — a cascade, unlike `detachAccountTransactions`, where what is left is the money and the money still moved.

  **One movement of money may be divided between categories.** `splits` is null, or a list of two or more `{ id, budgetId, amountCents }` parts adding up to `amountCents` **exactly** — enforced in `RULES`, and the rule the whole feature rests on: below it the envelopes read the parts while every balance reads the whole, and the two agree only because of it. Parts on the one record rather than a parent and its children, the transfer's choice for a sharper version of the transfer's reason — two rows that can be edited apart will eventually disagree about the amount, and the division then creates or destroys money. A part names a category and carries a **positive** amount: money left unfiled inside a split would be indistinguishable from a smaller transaction, and a negative part would be a refund hiding inside an expense. While a record is split its own `budgetId` is **inert but kept**, the switched-away-from rule again — it is what the record falls back to when the division is undone. Because the sum rule names `amountCents` as well as `splits`, retyping the total alone is refused, which is why the register sends a split row's figure to the editor instead of taking it in the cell. `migrateSplits` is the one migration here that **drops** what it read — a division that does not add up loses the division and keeps every cent, because no money is lost by falling back to one category and an incoherent split is the single state in which the two cuts of the books disagree. Repairing one would invent a decision nobody made, the reason an undated record is never given today's date. `reassignBudgetTransactions` moves a part like any other filing and **merges two that land on one category**; merging down to a single part ends the division, since a division of one is the record it already was.

  **`budgetLegs(transaction, insideBudget)` is what every consumer reads**, and it returns a **list** — one leg per part, one leg for an undivided record, and none at all for a transfer the budget never sees. One list and the same list on both sides of the identity, which is what makes it impossible to count a split or a transfer as cash on one side and miss it on the other.

  **A `transfer` is the third kind and the only record that names two accounts** — `accountId` is where the money left, `toAccountId` where it arrived. One record, not a linked pair: a pair would need every mutator to keep two rows in step on the amount, the date and the description, and one leg orphaned by a missed cascade would create or destroy money in a ledger whose one invariant is that the sums cover every row. One record cannot disagree with itself, so a delete stays a delete and a patch stays a patch. **What a transfer means to the budget is `budgetLegs`' answer and depends on nothing but which side of the boundary each account sits** (`insideBudget`, a new pure export on `AccountsContext`, for which **`null` is inside** — a detached side keeps its money in the envelope maths, the stance `accountBalancesAt` already takes):

  | source | destination | budget effect |
  |---|---|---|
  | spends through | spends through | **none** — a card payment, checking → savings |
  | spends through | off budget | an **outflow** against `budgetId` — a 401(k) contribution |
  | off budget | spends through | **income to assign** — a withdrawal into checking |
  | off budget | off budget | **none** — a rollover |

  Row one is why a credit card can finally be paid off: the money was budgeted on its way out *through* the card, so settling it is not a second call on any envelope, and on-budget cash is unmoved because the card's balance rises by what checking loses. Row two is exactly what the app already did when a contribution was filed under a savings category — what is new is only that the holding is credited too. **The store deliberately does not check the matrix**: `TransactionsProvider` is mounted *above* `AccountsProvider` so a delete can detach transactions, so it cannot see a scope. That is the shape of the bound `DonationsContext` cannot check, and it is answered the same way — `AddTransactionModal` refuses a boundary-crossing transfer with no category, and `budgetLegs`' consumers fall back to `UNCATEGORIZED_BUDGET_ID`, so the identity holds whatever reaches storage. A `budgetId` or a `toAccountId` left on a record that has stopped needing it is **kept, not cleared**, inert until it means something again — the rule a switched-away-from pay cadence follows. **Money arriving from outside the budget is the one place a split is not read**: it is income to the pool, and there are no categories in the pool, so a division on it is inert in exactly the same way. `detachAccountTransactions` cuts **both** sides.
- **`PayeesContext`** — `payees`: `{ id, name, defaultBudgetId }`, who the money went to. The transaction names it by **id**, which is the whole point — a rename is one write and every row that names the payee follows it, because no row was ever holding the name. `defaultBudgetId` is nullable and `null` is the ordinary case; it is **a default and nothing more**, the rule a recipient's `deductible` flag and a group's bucket both keep, so correcting where a shop is usually filed in March cannot restate what was filed in February. It is **not checked against the live categories and nothing cascades into it** — a default naming a deleted category is *inert but kept*, the switched-away-from rule, resolved where it is read (`AddTransactionModal` already guards a seeded category; `PayeeList` gives a stored-but-unknown value an option of its own). **Two normalisers with different jobs**: `normalizePayeeName` (trim, collapse, lowercase) is **identity** and the only thing the clash check reads, while `searchKey` in `src/payeeSearch.js` also drops punctuation so typing "att" finds "AT&T" — folding punctuation into identity as well would refuse to let "ATT" and "AT&T" both exist, and they may be two real payees. `deletePayee` detaches its transactions and keeps them, `deleteRecipient`'s rule. `mergePayees({ fromIds, intoId })` is what the entity exists for: several sources at once because a household tidying up is dealing with a cluster, **the whole batch validated before anything is written**, the **ledger written first** (rows pointing at a payee that still exists is a merge that did not happen; payees deleted out from under their rows is not survivable), and the survivor **adopts a default only where it has none of its own**.
- **`SchedulesContext`** — `schedules`: `{ id, kind, payeeId, amountCents, accountId, budgetId, description, cadence, startDate, endsOn, enteredThrough }`, the transactions the household already knows about — rent on the 1st, the quarterly premium, a second paycheque. **A schedule is a standing intention and holds no money**, the split `SavingsGoalsContext` keeps against its assignments and `BudgetsContext` against the ledger: what is *expected* lives here, what happened lives in the ledger, and no envelope, balance or report reads this store — so adding a schedule cannot move a figure anywhere in the app. **Nothing posts itself**, and that is the honest design rather than a limitation: nothing in an app with no backend runs at midnight, so a store that wrote its own rows would be claiming the rent went out on a day nobody opened the app. What it buys is that the row is *offered*, pre-filled, the moment it is due, and that an unpaid one stays visible as unpaid. **`enteredThrough` is the cursor and the one stored date** — every occurrence on or before it has been entered or deliberately skipped — because the occurrences are a closed form over `startDate` (the rollover rule) while a *decision* cannot be derived: the books cannot tell "the rent is unpaid" from "the rent was paid in cash and never recorded". It is deliberately **not** a `scheduleId` on the ledger, which would make "has this been entered?" derivable and then let correcting a rent payment's date silently un-enter it and offer the row twice. **Every reference is inert but kept**, the payee-default rule — this store reads no other, so a schedule naming a deleted account is resolved where it is read, and the enter form refuses rather than writing against it. Nothing cascades either way, so this provider's position in the order is free. **Two kinds, not three**: a transfer is not schedulable, since what one means to the budget depends on which side of the boundary each end sits and that rule already lives in `AddTransactionModal`.
- **`EmergencyFundContext`** — one record, `emergencyFund`: `{ targetSource, monthsCovered, targetCents, accountIds }`, how long the household means to be able to carry itself and where the money for it sits. **It holds no money and derives no target** — the split `SavingsGoalsContext` keeps against its assignments, one step further: what is stored here is the *shape of the question*, and the figure is `useEmergencyFund`'s, because it is a join across the plan and the balance sheet. **The target comes off the essentials bucket rather than being typed**, which is the whole point: an emergency fund is not a round number somebody likes, it is however long the household could cover its own necessary spending with no income — and the app already asks which categories are necessary, so a hand-typed figure would be a second, staler copy of an answer the books already hold. Raise the rent on the plan and the fund that has to cover it rises the same day. **Both answers are kept**, the `RetirementContext` rule: `targetSource` says which is in force and the other is left alone, because comparing "six months of essentials" against "fifty thousand" is the point and a switch that destroyed what it switched away from could only be used once. A typed figure is a real answer rather than an escape hatch — a redundancy package in mind, or essentials not all on the plan yet, is something the derivation cannot know. `monthsCovered` has **no blank state** unlike every other nullable field here: there is always a multiple in force, so an empty one would be a target of nothing rather than a question left open, and the field puts the old figure back. Capped at `MAX_MONTHS_COVERED` (120, the report window's ceiling) because past that the figure has stopped being a buffer and become a retirement plan, which this app answers elsewhere and properly. `accountIds` is the question `RetirementContext` asks about retirement money, answered the same way — **inert but kept**, never checked against the live accounts, so an id whose account was deleted reads as an account contributing nothing. **`accountAmounts` (id → cents) lets part of a ticked account be the fund**, because almost nobody opens an account only for this; absent is the whole balance (what a tick always meant), the figure counted is never more than the account holds, and an amount survives its account being unticked. `setFundAccountAmount` sets one — blank removes it, junk, zero and negatives are refused. Empty rather than "every cash account": which account is the buffer is a judgement, and guessing it would put a figure on screen nobody agreed to. Nothing cascades either way, so this provider's position in the order is free.
- **`AssignmentsContext`** — `assignments` per (budget, period): what was **actually put in**. Does *not* carry forward (the balance does). Zero rows pruned; negatives allowed — under rollover that is the only way to pull money back out. **`moveBetweenBudgets({ fromBudgetId, toBudgetId, period, amount })` is envelope budgeting's other everyday act**, beside assigning income: groceries came in under and dining out went over, so the difference moves across. It was always *expressible* — assign the source less and the destination more — but only as two edits, with the pool briefly inflated by money that was never free and the user holding the arithmetic in their head in between. **One `setAssignments` call, so the two deltas cancel and `toBeAssigned` is untouched by construction**: the identity in `dataModel.test.js` holds at every commit rather than only once both halves have landed, and a failure between them cannot park money in the pool. A move is a positive amount in a stated direction, so zero and negative are refused rather than quietly reversing the two selects. It is deliberately **not** refused for leaving the source overdrawn — this store sees only assignments, so it could not check it, and covering one category out of one that has not been funded yet is a real thing to want in the week before a paycheque. The app has exactly one way of saying so and it is the one it always had: the figure goes red.
- **`BudgetsContext`** — `budgets` and `groups`, plus one standing `plannedCents` **estimate** per category (the same figure in every period — it describes the category, not a month) and an optional `goalCents` **goal** beside it. The two answer different questions — what a category needs in a month against the balance it is saving towards — and only the goal is nullable: a blank estimate is a category nobody has made their mind up about and reads as zero, while a blank goal is a category not saving towards anything, which is most of them. So they are parsed by different functions: `readGoal` reads "" as `null` (the way a goal is *removed*) and refuses zero, a negative and junk alike, since a bad parse read as null would clear the goal the user was editing. `updateBudget` tells "leave the goal alone" from "take the goal off" through `readGoal`'s `stated`, not through `undefined`. Deleting a budget moves its outflows **and its assignments** onto `UNCATEGORIZED_BUDGET_ID`; dropping the funding instead would ask the user to fund the same purchase twice. Also owns **buckets** (`PLAN_BUCKETS`, in `PLAN_BUCKET_ORDER`: essentials / fun / savings / retirement — most necessary first, retirement last because it is the longest horizon of the four). Four and not three, because **retirement is split out of savings rather than folded into it**: both are money set aside rather than spent, but a house deposit or an emergency fund is still liquid and still the household's to redirect, while a Roth contribution is not really being saved *for* anything else. Folding them together would overstate savings as a share of the plan and — through `useRetirementProjection`, which seeds `annualContributionCents` off the retirement bucket — would let a down-payment fund inflate what the household appears to be setting aside for retirement by exactly as much as a real contribution. **Pre-tax payroll deductions never appear in any bucket**: a 401(k) leaves the paycheque before it reaches an on-budget account, so it never becomes a transaction to categorise, and `RetirementContext`'s `pretaxContributionCents` is where that half enters the plan instead. `DEFAULT_BUCKET` is essentials rather than a fifth "unsorted" one — a category nobody has classified is being paid for regardless, and counting it as a want or as saving would flatter the split. **Every category carries a real one — there is no "ask my group" state.** A group's bucket is only the value a new category *starts* on: `addBudget` resolves it once, at creation, and the record states its own from then on. So moving a category between groups, renaming a group, restating a group's bucket, and `deleteGroup` all leave what a category counts as alone — none of them can move money between the shares of the split as a side effect. `updateBudget` refuses `null` like any other non-bucket. The migration stamps a stored `null` with its group's bucket (read from the `budgetGroups` key by `storedGroupBuckets`), which is what the category was already counting as. `toSections` still hands every row an `effectiveBucket`; it now equals `budget.bucket`, with the section as a fallback only for storage edited by hand.
- **`AccountsContext`** — `accounts` (set up on Configuration, since the list is a standing fact) and `balances` per (account, period) — a statement figure, which **any** account may carry, read only by `useNetWorth` and never by the budget's own maths. `setPeriodBalances({ period, entries })` writes a whole month at once, validating the batch before writing any of it, and `setBalanceHistory({ months })` carries that rule up a level for the backfill grid — a window of months lands in one commit or none, so a year of history cannot end up half written. Both fold through the same `validateBalanceEntries` / `applyPeriodBalances` pair. **A blank amount deletes that row rather than storing zero** — unlike assignments, zero is a real balance here (a card paid off) and "never updated this month" has to stay distinguishable from it. `addAccount`/`updateAccount` validate a name, a type, a scope, an asset class from `ASSET_CLASSES`, and an **opening balance**; a liability stores `UNCLASSIFIED`, since asset class means nothing on a debt. **`AddAccountModal` does not ask for the class** — it was a question households could not usefully answer and only the net-worth bands read it — so `assetClassFor` derives it: an asset keeps the class it already has, and a new one is Cash on budget and Stocks off it. `updateAccount` validates the record **as it would stand after the patch**, so a partial update cannot slip a combination past the checks a whole one gets — and where the patch names `opening` (the form's dollar string) it **drops the stored `openingBalanceCents` before validating**, or the cents already on the record would win validate's `??` and the retyped figure would be taken and silently discarded. **`openingBalanceCents` is signed** — `signedOpeningCents` negates a liability, because the form asks a debt for the amount *owed* as a positive figure; `toStoredBalanceCents` / `toEnteredBalanceCents` are that same conversion exported as a pair, so the two forms that ask for a balance cannot come to disagree about which way a mortgage points. `openingDate` may be `null` (undated, counts from the beginning of the books). **`ACCOUNT_SCOPES` (on-budget / credit-card / off-budget) is an axis of its own, orthogonal to `type`** — a card is a liability spent through and a mortgage one that is only watched, so never treat scope as a subdivision of assets. **Only the off-budget line is load-bearing in the maths**: every derivation asks `spendsThroughBudget` (or its complement `isOffBudget`), which is true of on-budget accounts and cards alike, so a card's opening balance reduces "to be assigned", its balance derives from the ledger, and it is offered in the transaction form. A card is always a liability — `validate` refuses the asset combination, and `AddAccountModal` stops asking the kind question once the card scope is picked. Credit cards get a section of their own on `AccountList` because the total owed is the figure that panel is read for; the maths is unchanged by that split. `scopeLabel` is the shared display name. `DEFAULT_SCOPE` is on-budget, which is also what `migrateAccounts` stamps on a record saved before the field existed — and what an unrecognised scope falls back to everywhere. Deleting an account drops its `balances` but **keeps its transactions**, detaching them. `AccountList` divides by scope first and calls out owned/owed as an inner band only when a section holds **both**, and every row carries **Edit** beside Remove — editing is `AddAccountModal` opened on the record (`account` prop), never typing over the name in the list the way a category is renamed on the plan, because an account is six interlocking answers and a row of inline controls cannot express an answer that removes the question below it. Renaming through delete-and-re-add would take the account's `balances` with it, which is what the edit path exists to avoid. Also carries **`reconciledOn`** — the day the account was last checked against a statement and agreed. Stored, not derived: it is the one fact no ledger can know. `reconcileAccount({ id, date })` is a mutator of its own (defaults to today, `null` clears it) rather than a field on `updateAccount`, because it records something the user *did* rather than restating what the account *is*. A record predating the field reads as never reconciled, not as reconciled today.
- **`IncomePlanContext`** — the paycheques the user *expects*, by cadence. Independent of the ledger in both directions: nothing maps a transaction to the source that predicted it, so neither delete may cascade into the other.
- **`PayScheduleContext`** — one record, `{ cadence, lastPaidOn, periodDays, daysOfMonth }`: the calendar half of the income question, where IncomePlan is the amount half. **The cadence decides which of the other three fields mean anything** (`src/paySchedule.js` owns that mapping), and the ones it does not read are **kept, not cleared** — switching between fortnightly and twice-monthly to see which describes a new job is the point, and a switch that destroys what it switches away from can only be used once. Every field is nullable and independent, because part of a schedule is a real intermediate state and refusing it would blank the field the user just filled in. `cadence` has **no default**: most people are paid every two weeks and the ones who are not are exactly the ones a guess would mislead. A whole-value guard rather than a field-presence migration — the one thing it upgrades is a schedule stored as a bare day count, through `cadenceForDays` (7 → weekly, 14 → fortnightly, anything else → the custom interval), which is also what a `periodDays` set while no cadence is stated names itself. Read through `useNextPaycheck`.
- **`RetirementContext`** — one record, `retirementPlan`: the ages, the rates, and what the plan is counting on. A store of *guesses*, outside the books, and the separation is load-bearing — the projection reads across the stores but nothing flows back, so a scenario moves no money. **Two questions here have two legitimate answers each, and both are stored**: the starting point is either the accounts the user ticks (`accountIds`) or a figure they type (`startingBalanceCents`), and retirement spending is either a share of today's income (`incomeShareBps`, default 7000) or a typed figure (`annualSpendingCents`). A `…Source` field says which is in force and **the other is kept, not cleared** — toggling to compare is the point, and a toggle that destroys what it toggles away from can only be used once. **`pretaxContributionCents` is the one figure here the projection cannot derive**, and that is why it is stored rather than read off the books: a pre-tax payroll deduction leaves a paycheque before the money ever reaches an on-budget account, so it never becomes a transaction and never gets a category or a bucket. Everything else the projection reads comes from an account, an income source, or the retirement bucket; this is the half of the contribution that has no such home. `null` means **none**, not "not yet known" — most years it really is zero for a household with no payroll plan, and treating a blank as unstated would understate every projection until the user happened to find the field. `annualContributionCents` is `null` for "whatever the plan already sets aside", which is the **retirement** bucket's estimates annualised **plus `pretaxContributionCents`** — deliberately not the savings bucket, since a house deposit sits there too. A typed figure overrides that combined total rather than only the derived half. `usePlanHealth` grosses the same pre-tax figure onto **both** sides of its balance — `expectedIncomeCents` and `plannedCents` alike, and onto the retirement bucket's own share — so "left to plan" is unmoved by a figure that never touches a real account, while neither what the household earns nor what it sets aside is understated. The rates carry real defaults, because unlike an age they have a defensible standing answer: `growthRateBps` 1000 while saving, `drawdownRateBps` 550 once retired, `inflationRateBps` 250. **All three are nominal — before inflation** — which is why the first is ten and not the seven a saver usually quotes: seven is the long-run *real* equity return, already net of inflation, and the projection deflates what it is given rather than assuming it has been deflated already. Entering seven here takes the haircut twice. The pair is set so what comes *out* is roughly the 7% real while saving and 3% real once retired that a planner actually means. **Coherence between fields is *not* checked here** — retiring before you were born is reported by the projection as something it cannot answer yet, because refusing the field the user just typed is the one response that makes a plan uneditable. A whole-value guard rather than a field-presence migration, like `PayScheduleContext`; the key is `retirementPlan`, and the scaffold's `retirementAssumptions` (rates as fractions, a withdrawal rate this plan has no use for) is left in storage unread.
- **`DonationsContext`** — giving, in three keys and **no money**: `donationRecipients` (the organizations), `donations` (one statement per gift), `donationGoals` (one per year). **A donation is not a movement of money, it is a statement about one.** A gift is an ordinary outflow on the register — it leaves an account, comes out of a category, counts against an envelope and appears in the spending report — and the record here is keyed on that transaction's id and carries nothing the ledger already holds: no amount, no date, no account. Copying the amount would give the household two figures for one gift and no way to tell which is the money. `{ transactionId, recipientId, deductibleCents, acknowledged }`. **`deductibleCents` is stated on every gift — there is no "ask the organization" state**, the same rule as a category's bucket: a recipient's `deductible` flag is only what a *new* gift starts on, resolved once at entry, so correcting an organization's status in March cannot restate what a return filed in February claimed. It is also the only form that covers a $200 gala ticket against an $80 dinner. **The one bound this store cannot check is "no more than the gift itself"** — the amount lives on the transaction, which it does not read — so the forms check it where the figure is in hand and `useGiving` clamps what it reads. Deleting an organization **keeps its gifts** and detaches them (`recipientId: null`), the same way spend outlives its category; deleting the transaction removes the tag, and untagging leaves the money alone. `recordDonation` is idempotent on the transaction id — one movement of money is one gift, so recording twice restates rather than duplicates. A goal is `{ year, source, amountCents, shareBps }` with **two legitimate answers and both kept** (`GOAL_SOURCES.AMOUNT` / `INCOME_SHARE`), the `RetirementContext` rule for the same reason: comparing "a tenth of what we earn" against "six thousand" is the point, and a switch that cleared what it switched away from could only be used once. Blank takes a goal off; junk is refused. `ACKNOWLEDGMENT_THRESHOLD_CENTS` (25000) decides nothing — no figure moves because a receipt is missing — it only decides which gifts `useGiving` reports as still needing one.
- **`LifeEventsContext`** — `lifeEvents`: `{ id, name, kind, startAge, years, oneTimeCents, annualCents, keptShareBps, enabled }`, the dated changes the net-worth projection walks through — a wedding, childcare, a sabbatical, Social Security, a house. **A store of guesses holding no money**, read by `src/netWorthProjection.js` and nothing else. Five kinds (`LIFE_EVENT_KINDS`, owned by the projection module and re-exported here): an **expense** and an **income** carry a one-time figure, a yearly one, or both, as magnitudes — the direction is the kind, the ledger's rule — and an **income change** carries the share of normal pay kept (0 for a year off), which scales take-home, pretax and the budget's saving together but never the spending. **Buying a home** adds `priceCents`, `downPaymentCents`, the mortgage's nominal `rateBps` and `termYears`, and `rentSavedCents`, reusing `oneTimeCents` for closing costs and `annualCents` for what owning costs a year; **selling one** names `propertyRef` (a property-band account or a purchase event's id), optionally the `debtRef` it pays off, and `sellingCostBps`. Both references are **inert but kept** — the walk skips a sale whose property it cannot find. **`years`, not an end age**, so whether the last year counts is never a question; `null` runs for the rest of the plan. Fields a kind does not read are kept, and `enabled` leaves an event out without deleting it, which is what scenarios will be built on. An event seeded from a savings goal or a template is **copied once**, never linked, so nothing cascades either way and the provider's position is free.
- **`ScenariosContext`** — `retirementScenarios`: at most `MAX_SCENARIOS` (4) of `{ id, name, plan, enabledEventIds, slot }`. **A scenario is a snapshot, not a link**: the whole retirement plan is copied, so editing the live plan cannot change what a saved one says, while events are named by **id** — an event is already a record, and a scenario is a choice about which are on, so "buy" against "rent" is two events and one scenario with each. A deleted event's id is inert; an event added since is off in every scenario saved before it. **Four, because the comparison chart has four measured hues** (the bucket colours), and **`slot` is the colour**: the lowest free one at save time, stored and never moved, so removing a scenario cannot repaint the rest. Names are unique by trimmed, case-folded form. Using a scenario is the page's write — `replaceRetirementPlan` (the plan through `migratePlan`, now exported, so an older snapshot gains the fields it predates) and `setEnabledEvents` — and never touches the books. Nothing cascades either way.
- **`RewardsContext`** — three keys and **no money**: `rewardsBalances` (`{ id, programId, holder, points, asOf }`, one per program per person), `rewardsValuations` (`{ [programId]: valuePer100Cents }`, only where the household's figure differs from the catalog — blank removes it so the program follows the catalog again) and `rewardsTrips` (`{ id, name, date, programId, points, taxesCents, cashPriceCents }`). **Points are not money until redeemed and a valuation is a judgement**, so nothing in the books, net worth or any report reads this store — the `RetirementContext` split. **Programs come only from the built-in catalog in `src/rewards.js`**, and a stored record naming an id the catalog lacks is dropped on the way in: there is no other store a program could have been deleted from, so an unknown id is one a newer build removed and nothing could show it. **A point's value is an integer number of cents per hundred points** (`valuePer100Cents`: 1.3¢ is 130), the cents discipline one step down, because fractional cents per point are the ordinary case. `summariseRewards` is the whole page as a pure function: programs summed across holders at the resolved value (override, else catalog), and each trip's achieved value per point — the cash fare less the taxes still paid, over the points — against that valuation, with funding from the program's own balance first and then by transfer from bank currencies, largest balance first, **in date order so no point is promised to two trips**, and a ratio's cost rounded up so a trip marked covered really is. Transfer partners are listed for bank currencies only and change without notice, which the page says. Nothing cascades either way, so the provider's position is free.
- **`SavingsGoalsContext`** — `savingsGoals`: a **standing intention**, `{ id, name, targetCents, targetDate }`, for the medium-term thing expected to *exceed* a normal month — a camera, a wedding, a special event — which is exactly what makes it a goal to plan around rather than a category to estimate. It holds **no money**: what has actually been put toward it lives next door, on the same split `BudgetsContext` and `AssignmentsContext` keep, and for the same reason — the target is the estimate, the assignment is the money. `targetCents` must be a whole number **greater than zero**: a goal of nothing is not a goal, and unlike a category's `goalCents` there is no "not saving towards anything" state to express, since that is what having no goal record already means. `targetDate` is nullable — a goal with no date in mind is still a goal — and is `"YYYY-MM-DD"` or refused. A goal names **no category, no account and no transaction**, so nothing outside this pair deletes into or out of it; `updateSavingsGoal` refuses an id it cannot find rather than letting a `map` that matches nothing report the write as landed, because `useSyncedState` syncs a delete from another tab — or from another device — and the edit modal can be open on a record the store no longer has.
- **`SavingsGoalAssignmentsContext`** — `savingsGoalAssignments`, one record per (goalId, period): what was **actually put in**, the same shape `AssignmentsContext` keeps for budgets. Zero rows are pruned — "assigned nothing" and "never assigned" spend the same — and negatives are allowed for the identical reason a category's are: pulling money back out of a goal over-funded in an earlier month is the only way to move it, and refusing that leaves the user with money they can see and cannot reach. **There is no day-one seed**, unlike `AssignmentsContext`: a goal has no ledger of its own to have already spent from, so a ledger that predates the feature has nothing to seed here. `setPeriodAssignments({ period, entries })` validates the **whole batch before writing any of it**, so a bad figure in the ninth goal cannot land after the first eight have already committed — the rule `AssignmentsContext` and `setPeriodBalances` both keep, and the one that makes `AssignIncomeModal`'s single submit safe. `removeGoalAssignments` is the cascade `deleteSavingsGoal` calls.

Mutators that can reject input (`addBudget`, `addTransaction`, `updateTransaction`, `addAccount`, `updateAccount`, `reconcileAccount`, `setAssignedAmount`, `setPeriodAssignments`, `moveBetweenBudgets`, `setBalance`, `setPeriodBalances`, `setBalanceHistory`, `setPaySchedule`, `setRetirementPlan`, `setEmergencyFund`, `addRecipient`, `updateRecipient`, `recordDonation`, `updateDonation`, `setGivingGoal`, `addSavingsGoal`, `updateSavingsGoal`, and the savings-goal `setAssignedAmount` / `setPeriodAssignments`) return `{ ok, error }`. `deleteSavingsGoal` is the exception in that pair and deliberately so: a goal holds no money and nothing else names its id, so there is nothing a delete could be refused for. **Callers must surface the error** — never close a modal as though the write succeeded. Each context memoises its value.

## Envelope budgeting (`src/hooks/useEnvelopes.js`)

The first of **eight** hooks that read across stores. The eight, so the count is checkable rather than folklore: `useEnvelopes`, `useAccountBalances`, `useNetWorth`, `useRetirementProjection`, `useSpendingReport`, `useGiving`, `useSavingsGoalEnvelopes`, `useEmergencyFund` — each owns a definition no single store can own, and the sections below number themselves against that list. `useDashboard` and `useStartingBalances` are not in it (they arrange or re-window what `useEnvelopes` already derived), nor is `usePlanHealth` (it crosses three stores but never reads the books at all), nor `useNextPaycheck` (one store), nor `useUpcoming` — also one store, and it **must not become** a cross-store hook: a schedule is a prediction, and a hook that read the ledger would invite matching an occurrence against a transaction that looks like it, which is guesswork about intent and wrong the first time a bill is paid twice on purpose.

**`src/recurrence.js` is which days a recurring bill lands on**, a pure module like `paySchedule.js` and `chartAxis.js`, and the third in that family — `cadence.js` answers what a recurring figure comes to in an average month (no dates in it), `paySchedule.js` answers when the household's own paycheque lands. Four cadence names appear in all three tables by coincidence of English and **they are not to be consolidated**: the proof is the weekend rule, which `paySchedule.js` has and this must not — a payday on a Saturday is paid the Friday before because that is what payroll does, while a direct debit on a Saturday is taken on the Saturday, and lending payroll's courtesy to a water bill would report every bill due on the 1st of a month starting Sunday as due two days early. **A schedule is anchored on one date and stepped**: every occurrence is computed from `startDate` rather than from the one before, which is what stops a bill due on the 31st from ratcheting down to the 28th forever the first time it passes February. Nothing here is stored. `useUpcoming` is the join to the calendar, and it owns the one rule the arithmetic cannot state: **the window opens at the cursor, not at today**, so a bill due on the 1st that nobody entered is still on the list on the 9th, marked overdue — a list starting at today would let it vanish in silence, which is the one failure a bill reminder cannot have. One row per **occurrence**, not per schedule, since a weekly bill is genuinely four things to do this month and each is entered or skipped on its own.

**Every record is read through `budgetLegs` first**, and it is a *list* because one movement of money can be divided between categories: a receipt split three ways is three legs against three envelopes, adding up to the one figure the account lost. It is also what makes a transfer three-quarters invisible here: money moved between two accounts the budget spends through is still exactly where the budget thought it was, and only a transfer that *crosses* the boundary moves anything — out of the budget it is spending against its category, into the budget it is income to assign. Both sides of the identity below are built from those same legs, so neither a split nor a transfer can be counted as cash on one side and missed on the other.

`useEnvelopes(period)` returns one row per budget id, one row per savings goal, and the pool:

```
activity(b, p)   = refunded(b,p) − spent(b,p)          ← signed
available(b, P)  = Σ over p ≤ P of [ assigned(b,p) + activity(b,p) ]
carriedIn(b, P)  = the same sum over p < P
available(g, P)  = Σ over p ≤ P of assigned(g,p)       ← a goal, and nothing else
toBeAssigned(P)  = opening(P)
                 + Σ over p ≤ P of [ poolIncome(p) − Σ over b of assigned(b,p)
                                                   − Σ over g of assigned(g,p) ]
```

**A savings goal draws on the same pool a category does.** A dollar diverted to the wedding fund is a dollar that cannot also fund groceries, because it is the same paycheque — so a goal's assignment subtracts from `toBeAssigned` exactly as a budget's does, and there is no second pool anywhere.

**The invariant**, asserted after every mutation by the tripwire in `dataModel.test.js`:

```
toBeAssigned + Σ available + Σ goal available === opening + cumulative inflow − cumulative gross spend
```

The assignment terms cancel algebraically, so this checks coverage, not arithmetic. Four conditions keep it true:

1. **`rows` is the union** of budget ids, the Uncategorized sentinel, and every id appearing in the ledger or in `assignments`. Filtering what the *grid* renders is fine; filtering what the *sums* cover is not.
2. **Both sides use the same period filter.**
3. **A split's parts are its legs and nothing else is.** The sum rule in the store is what makes this safe: `cumSpentCents` here is built from the parts while `useAccountBalances` reads `amountCents`, so a division that did not add up would put the envelope view and the balance sheet on two different transactions with nothing downstream in a position to notice. `expectCoversLedger` in `dataModel.test.js` is the check that cannot be satisfied by both sides drifting together — it adds up the raw `amountCents` of every outflow in the seed and insists the envelopes cover exactly that.
4. **A refund is counted once on each side, by different routes.** `toBeAssigned` is built from `cumPoolIncomeCents` (uncategorised inflows only) while the identity's right-hand side uses `cumIncomeCents` (every inflow) and a **gross** `cumSpentCents`. Netting refunds off the spend as well would subtract them twice; adding them to the pool as well would create money.
5. **A goal's `availableCents` is nothing but its own cumulative assignment**, and that is what makes the third term cancel. A goal has no ledger — no spend, no refund, no activity of any kind — so what `goalAssignedThroughCents` takes out of the pool is precisely what `Σ goal available` puts back on the left, the way a budget's assignment and activity do for a category. **Give a goal any figure the ledger also sees and the identity breaks**, which is the whole reason a goal is not modelled as a category with an account behind it.

Also:

- **`opening` is the starting balance of the on-budget accounts**, reported separately rather than folded into `cumIncomeCents` — "income in August" is checked against payslips and an account opening is not part of it. Off-budget accounts are excluded: a 401(k) is not grocery money.
- **Rows carry `spentCents` and `refundCents` gross alongside the signed `activityCents`.** Use the signed one wherever the figures have to add up to the balance beside them (the dashboard table); use the gross ones only where the label says "spent" as a quantity.
- **Undated records count in every period's cumulative sums.** On a row they fold into `carriedIn`, never into this month's activity, so the displayed figures add up to the displayed balance.
- **Future-dated records are excluded** until their month arrives — hence the ban on mixing these figures with all-time ones.
- **Rollover is the closed form above**, not a stored carry-in, so past periods are not immutable.
- **The day-one seed** in `AssignmentsContext` opens every category with an assignment equal to its existing spend — walking a divided receipt's parts, so each category opens at its own part, so a pre-existing ledger starts at zero envelopes with net cash unassigned. It runs in the **lazy default only**, and reads storage through `readStoredLedger` because no provider is mounted yet.
- **"Fill" tops a category up to its estimate outright**, ignoring carry-in, so sinking funds accumulate.
- **A future-dated goal assignment must not seed a zero-valued `goalRows` entry**, and this is the one place a goal's row set behaves unlike a budget's. `rows` is a union with `budgets` and with every id in the ledger, so an out-of-window assignment that creates an empty tally bucket is harmless — the row would have existed anyway. `goalRows` has no such union to fall back on: **its row set *is* its tally**, built only from assignments that fall at or before `period`, so an assignment for a month not yet reached must be skipped outright rather than filed as a zero. Bucket it first and a goal funded only in December appears in June carrying $0, which reads on the page as a goal that exists and has been given nothing rather than one that has not started.

`useSavingsGoalEnvelopes(period)` is the seventh cross-store hook and the join on the other side of that: every goal from `SavingsGoalsContext`, against `goalRows`' figures for it, the same join `useDashboard` performs for categories and for the same reason — `useEnvelopes` knows the money, the goal store knows the goal, and neither may read the other. A goal with no assignments at all still gets a row, from a zeroed default, because the page's subject is the goals rather than the assignments. `remainingCents` is `target − available` **floored at zero**, so a goal met — or overshot, by a withdrawal that has not happened yet — never reads as owing money back.

## Account balances (`src/hooks/useAccountBalances.js`)

The balance-sheet cut of the same ledger: `balance(a, P) = opening(a) + Σ inflows − Σ outflows, through P`. Every dollar appears in both cuts — envelopes say what money is *for*, this says where it *is*.

**A transfer is the one record that moves two balances, and the one the two cuts read most differently**: here both halves are always real, while the envelope cut sees a transfer between two spend-through accounts as nothing at all. Each side is credited only if it still exists, so a transfer whose holding was deleted still leaves the account it left — the detached-record rule, applied to a record with two ends.

**A division between categories is invisible here**, and that is the seam the sum rule buys: what an account lost is `amountCents`, whatever the envelopes make of it.

**Derived, never stored**, which is what separates it from `balances` in `AccountsContext` — that is a hand-entered snapshot, the figure read off a statement. **This hook never reads one**, whatever account it belongs to: what the budget may spend, and what Configuration reports beside each account, is the books' own arithmetic. A snapshot changes what an account is worth on the *net-worth* view and nothing else, which is the seam that keeps the envelope invariant true. Only on-budget accounts are offered in the transaction form, for the same reason as ever.

`accountBalancesAt(accounts, transactions, period)` is the derivation as a plain function; the hook is a `useMemo` over it. **It stays the only definition of what an account holds** — `useNetWorth` runs it once per month across a chart window rather than writing a second one that could drift from the figure shown beside it on Configuration.

## Net worth (`src/hooks/useNetWorth.js`)

The third of the eight cross-store hooks, and the join between the app's two ways of knowing what an account holds: the ledger's arithmetic, and the figure the user read off a statement. **Every account can carry both** — a month's snapshot is a record of the whole position, and the everyday accounts are half of it. What differs is the fallback, and the asymmetry is the design:

```
off budget    → snapshot at or before P, else derived   ← carries forward
spent through → snapshot for P exactly,  else derived   ← never carries
```

A 401(k) is worth what the market says, which no ledger can know, so May's figure is the best answer available in June. An everyday account's balance is live arithmetic: a statement read in May is the better answer *for May* — it catches what the books missed, and before the books opened it is the only answer at all — but standing in for June would freeze the account and hide every transaction logged since. So it answers for its own month and hands back. An off-budget holding's derived figure is now its opening balance **plus whatever has been transferred into it** rather than the opening alone — a real reading, but an incomplete one, since what it is missing is every dollar the market added. That gap is growth rather than a disagreement about the books, which is why `driftCents` is still `null` for one. Where both exist on a spend-through account, `driftCents` is the difference; **the hook reports it and never resolves it** (that gap is what a reconciliation is for), and `describeSource` is the one place the wording for it lives, shared by `HoldingsTable` and `UpdateBalancesModal` so the two screens cannot describe the same figure differently. **What closed the other half of that is `FixDriftModal`, not a change to the arithmetic**: the user says which record is right and the app writes an ordinary transaction for the difference — an **inflow** where the statement is higher (money arrived that nobody wrote down, so it is income waiting to be assigned) and an **outflow** where it is lower, which has to name a category like any other spending. A fourth kind of "adjustment" record would need a rule in the envelope identity, the balance sheet, the spending report and the drift figure itself, and the first consumer to forget it would break the invariant; two kinds the ledger already has need none. It is dated **inside the statement's month** — month-end, or today where that is the current month, purely so the register shows no future date — because the gap is a disagreement about *that* month and a correction landing in this one would leave it standing. Nothing is reconciled by it: stamping the account checked is its own act, on the dashboard.

**Snapshots carry forward, never back.** A holding last valued in May is worth May's figure in June and July — which is what makes a once-a-month update enough — but in April it is worth its opening balance. Propagating the earliest figure backwards would draw a flat line across years nobody recorded and present it as history.

**`chartSeries` is `series` with every account's figure smoothed between the real snapshots that bracket it, and it exists for exactly one reason: the chart and its table twin.** A holding entered in January and not touched again until June reads, in `series`, as January's figure held flat for four months and then a jump — the true record of what was actually entered, and what `current`, `changes`, `rows`, `tracked` and `driftCents` all need, since whether a holding is stale and what it is worth *right now* are questions about the real snapshots. `chartSeries` answers a different question — the probable shape of the account across the gap — and asks it of a spend-through account exactly as it does of an off-budget holding: a household whose ledger for that account only starts partway through its history leans on backdated statements for the months before that, and the chart bridges those the same way a 401(k)'s gaps get bridged, rather than showing the ledger's own (often empty) reading for months a statement already answered for. It bridges only real data: before the first snapshot or after the last there is nothing to draw a line to, so the same carry-forward/opening-balance fallback stands for an off-budget holding, and the same hand-back-to-the-ledger fallback stands for a spend-through account — a lone reconciliation on an otherwise fully-tracked account never gets carried forward on the chart either, exactly as `series` never carries it. An account with no bracketing pair of real snapshots at all — the common case for a spend-through account whose ledger already answers for every month — is untouched by any of this.

**The line across an off-budget gap is bent toward where the money moved, not drawn straight — a spend-through account always takes the even ramp.** For an off-budget holding, an even month-by-month ramp is the right guess for a balance that simply grew, but a lump transfer out of a spending account (a down payment routed through a "Savings" category) makes an even ramp under-credit the holding for however long the gap runs, which reads on the total net-worth line as the money going briefly missing before "catching up": it never left, the account it was already in just hadn't been revalued yet. `indexSavingsSpend` sums, by month, two things that are the same fact recorded two ways: a **transfer** whose destination is off budget (whole, since a transfer names the account the money reached and no division of it changes that), and the parts of an outflow filed under one of the **`TRANSFER_BUCKETS`** — savings *and* retirement, counting only those parts, so a $300 supermarket shop with $50 put aside is fifty dollars of evidence rather than three hundred — since both name money leaving a spending account on its way toward a holding rather than being spent. A transfer names the account the money went to, so it is evidence rather than a guess and its category is not consulted at all; a categorised outflow names only a category, so it stays a **proxy**. Both are counted because a household will hold both — years of contributions recorded as savings-bucket outflows before transfers existed, and transfers from the day they did — and dropping either half would take the weighting out from under exactly the history it was drawn for. `interpolatedCents` weights the ramp by that figure instead of by elapsed months, still shared across every off-budget holding rather than attributed to one, since the proxy half cannot say which holding it was bound for. **Per-account attribution off the transfers alone is the next step here and deliberately not taken yet**: it would change the shape of every smoothed line, which is its own piece of work. Where a gap holds no transfer-bucket spend at all — most of them, where the whole change was market movement — it falls back to the even ramp. **A spend-through account's own recorded activity is deliberately not used the same way**: the whole reason its gap needs bridging is usually that its ledger is left-censored — tracking only starts partway through — so its activity clusters wherever tracking happened to begin, not wherever the balance actually moved. Weighting by it would credit the first tracked month with the entire change and draw every earlier month flat, the exact staircase this function exists to remove; the off-budget signal avoids that because it reads a *different*, presumed-continuously-tracked account's ledger.

**A spend-through account gets one further bracket besides its own typed statements, and it is automatic.** `withCurrentBridge` reaches from its last backdated statement toward `period`'s own live ledger figure — `current`'s `derivedCents` for that account — but only where the ledger has *nothing at all* recorded in the months strictly between the two (`indexAccountActivePeriods` / `hasActivityBetween`; `period` itself is never part of that check, since the ledger is definitionally expected to answer for it). That is what lets a household backfilling a partially-tracked account see a smoothed line all the way to the present without re-typing a reconciliation every month just to keep the bridge alive — the typed figure is still what makes a reading *real* (`series`, `current`, `HoldingsTable` never see this virtual bracket, only the chart does). And it is what keeps a lone reconciliation on an otherwise fully-tracked account from being second-guessed: any real activity recorded since the last statement, however partial, leaves the account untouched and its accurate in-between months exactly as the ledger reads them.

`NetWorthPage` is the one place both `series` and `chartSeries` exist side by side: `chartSeries` feeds `NetWorthChart` and its table twin underneath, everything else on the page — `NetWorthSummary`, `HoldingsTable`, `UpdateBalancesModal` — reads the exact figures.

`HOLDING_CLASSES` is a **coarser cut than `ASSET_CLASSES`**: cash / invested / property / debt, mapped by `BAND_BY_ASSET_CLASS` (total — an unmapped class falls to `property`), with any liability going to `debt` whatever it bought. Four bands is where a stacked chart stops being readable, which is also how many hues are validated against each other. `debtCents` is a positive magnitude (matching `owedCents`) with `0` written out rather than negated, since `-0` would travel into every comparison downstream — and `formatCents` normalises it too, because `Intl` renders `-0` as "-$0".

`useNetWorth(period, { months })` returns `series` (oldest first, ending at `period`) and its chart-smoothed twin `chartSeries`, `current`, per-account `rows` (each carrying `valueCents`, the `derivedCents` it would have had from the books alone, and `driftCents`), and `tracked` — **every** account, the list the monthly pass walks, with the month each was **last** updated. That is the account's own latest snapshot and not the one in force at `period`, so stepping back to March does not make a holding updated in August look untouched since February. `needsUpdate` is true only of a hand-valued holding with no figure for the month: an everyday account with none is not waiting on one, it is answered by the books, and flagging it every month would cry wolf.

**The chart is cut by account, not by band.** `buildSlices(accounts)` is the series list — one per off-budget account, plus `SPENDING_SLICE`, a single band holding every account the budget spends through — and each series entry carries `values` keyed the same way. The everyday accounts are working capital passing through rather than holdings, and four of them are four thin bands that change places with each other as the month is spent, so they get one band between them; the account-by-account cut of *those* is the register. Slices are ordered by band and then by the order accounts were added, **never by size**, or the stack reshuffles whenever two holdings cross and the reader reads the reshuffle as movement. `values` is signed and **a slice draws on the side its own figure puts it**, which is what lets the spending band be one series: a month whose cards outweigh its cash is genuinely negative working capital and draws below the baseline. The band totals (`cashCents` … `debtCents`) survive alongside for the summary tiles and `HoldingsTable`, which are the coarse cut.

`changes` is the headline change over each of `CHANGE_RANGES` — 1M, 3M, 6M, YTD, 1Y, 5Y, 10Y, ALL — each carrying `fromPeriod`, `fromCents`, `changeCents` and `changeBps`. **Each entry also carries `months`**, which is what a single entry means both things at once: `from(period, firstPeriod)` names the month the headline measures from, `months(period, firstPeriod)` sizes the chart's window, and picking one range picks both. The two are still allowed to disagree for the same key — "1y"'s window is the twelve columns ending at `period` while its `from` reaches one month earlier, to the month *before* the window opens, because a change "since a year ago" has always measured from outside the window it shares a key with (`netAt` is the fallback that lets it). YTD measures from **December of the previous year**, the close of the old year, not from January's close, and its `months` is the same count the other way — however many months of the year have happened. ALL is the one pair that reads the ledger: both its `from` and its `months` resolve against `firstPeriod` — the earliest month anything is known about the books, an account's stated opening, a snapshot, or a transaction, computed once by `firstKnownPeriod` and returned alongside `changes` — capped at the same **120 months** (`MAX_WINDOW_MONTHS`) `10y` already sits at, for the reason given there. `percentChangeBps` returns `null` for a base of zero or a base on the other side of zero from where the household ended up — −$10,000 to $10,000 is not "up 200%" — and the page prints a dash; the dollar change is always shown, so refusing to invent a percentage costs nothing. Where both are the same side, the denominator is the base's **magnitude**, so a debt shrinking reads as up.

**The Net worth page has a month on it and the dashboard deliberately does not.** Half of what is on it is typed in, and the month it was typed for is the meaning of the figure. The stepper is also the whole backfill mechanism for a *missed month*: step back, `UpdateBalancesModal` writes to the month on screen, step forward. There is no separate mode, because a month entered late is the same record as one entered on time — which is why the modal puts the month in its title.

**Two controls on that page**: the stepper picks the month everything is *as of*, and one `SegmentedControl` (`SPANS`: 3M/6M/YTD/1Y/5Y/10Y/ALL, a subset of `CHANGE_RANGES` filtered by key — 1M is left off, since a one-column chart is not a shape worth drawing) picks how far back both the chart *and* the summary's headline change look. `useNetWorth` takes the picked key as `spanKey` rather than a bare `months` number (though the numeric option still exists and still wins when both are given, which is what lets `useNetWorth.test.js` size a window directly without going through a span at all) and resolves both halves off the one `CHANGE_RANGES` entry, which is what makes this one dial instead of two that could disagree.

**Arriving with years of statements is the other shape of the same job**, and it gets `BalanceHistoryPanel` — a `<details>` closed by default at the foot of Configuration, holding a grid of a year's months × every account, committed through `setBalanceHistory`. Same records, different door: twelve open-and-close cycles of a modal is a chore, and the figures being entered are one series per account, which is a column. It sits on the page with no month in its corner because **every row names its own** — that, not the stepper, is what makes a grid safe there. It reads its own stores rather than taking props, since it needs the accounts, their snapshots and a per-month ledger balance; the last of those comes from `useNetWorth`'s own `series`, never from a second derivation.

**Blank cells are what both forms turn on.** A blank is a month nobody recorded, so what fills it is the fallback for that account — the books for one the budget spends through, the figure above for one valued by hand — shown greyed in the cell so the column reads as the series it is. Seeding a cell with the value it inherits would turn one statement into twelve records of it, which is also why `UpdateBalancesModal` starts a spend-through field **empty** with the ledger's figure beside it: only a typed figure becomes a record, so a monthly pass done on the 12th cannot freeze an account halfway through the month. In the grid, moving the window re-seeds every field, so an unsaved edit is lost — hence the warning beside the stepper while the form is dirty.

## Retirement (`src/hooks/useRetirementProjection.js`)

The fourth cross-store hook, and the only one that reads a store of guesses (the fifth through eighth are `useSpendingReport`, `useGiving`, `useSavingsGoalEnvelopes` and `useEmergencyFund`, below). It joins the plan's assumptions to three real figures: the ticked accounts at the value `useNetWorth` gives them (so a holding valued by hand counts at the figure the user entered), the expected income the spending target is a share of, and the **retirement** bucket the contribution defaults to — that bucket and not savings, plus the plan's own `pretaxContributionCents`, which no bucket can hold. **Nothing flows back** — no envelope and no balance moves because a scenario was explored.

**Everything is in today's dollars, and that is what makes the comparison honest.** The target is a share of what the household earns *now*, so the balance measured against it has to be in the same money: both rates are deflated once, `real = (1 + nominal) / (1 + inflation) − 1`, and the real rates are reported back so the page can print them beside the ones that were entered. Growing at a nominal 7% and measuring against a today's-dollars target overstates a thirty-year plan by about half, silently — it is the single most flattering error this kind of tool makes.

**Two rates, not one.** Money still being saved is a thirty-year bet; money being lived on is next year's groceries. The accumulation rate stops at the retirement age and the drawdown rate takes over.

```
need(S, n, d) = S × (1 − (1+d)^−n) × (1+d) / d      ← an annuity due
grow(b)       = b × (1+g) + C                        ← while saving
spend(b)      = (b − S) × (1+d)                      ← once retired
```

The withdrawal comes out at the **start** of the year and what is left grows, because that is the order retirement happens in, and `need` is the closed form that matches that recurrence exactly. **The tripwire in `useRetirementProjection.test.js` asserts it**: a balance of `need` on the first day of retirement is a balance of zero on the last. Any change to either half has to keep it green — that is the only thing keeping the closed form and the simulation describing the same plan.

**The series is the answer and the figures are read off it**, so the chart and the headline cannot disagree: `projectedCents` *is* the series' value at the retirement age. Only `need` and `requiredContributionCents` are closed forms, since neither has a simulation to read. Balances are floored at zero — a projection that draws a portfolio below the axis is drawing a debt nobody took on — and the year is called unaffordable only past `SHORTFALL_TOLERANCE` (a dollar), because carrying fractional cents through a sixty-year walk leaves an exactly-funded plan a fraction of a cent short of its final withdrawal, and a headline should not flip on that.

**`src/netWorthProjection.js` walks the whole balance sheet forward beside it** — cash, invested, retirement, property and each debt, from every account at `useNetWorth`'s value — and walks every enabled life event through it (`.claude/LIFE_EVENTS.md` is the plan). An event's income is spent before savings once retired, and a year it more than covers leaves the rest in cash. **A home is bought and sold in place at the start of its year**, sales before purchases so a downsizing can pay for the next one; each property is its own holding and each loan its own debt, because a sale names one. **A mortgage an event opens is paid on top of the budget** — today's budget cannot hold a payment that does not exist yet — where one already on the books is inside it. Every loan's payment is fixed in nominal dollars and made at the **end** of its year, deflated by `elapsed − since + 1`; dropping the `+ 1` overpays every year and ends a thirty-year mortgage two years early.

**The page's outlook is `retirementOutlook`, read off that walk, and `projectRetirement` is no longer what the page shows** — it stays as the pure function the reproduction tripwire holds the walk to. On course is the **liquid** money at the retirement age (cash and every investment, never the house); need is every retired year's draw — spending, debt payments and owning costs, less event income, with a sale's proceeds as a year that asks for less — discounted back as an annuity due at the drawdown rate and grossed up for tax on the pre-tax share. With one pot and flat spending that is `requiredNestEgg` exactly, which is why the old tripwire still means what it did. "Year by year" draws that liquid series against the need; **`NetWorthByAgeChart`** under "Net worth by age" draws the whole balance sheet as a column per age — the net-worth bands in their measured colours, retirement money at full `invested` and other investments at half, debt below the baseline by `stackPaths`' sign rule, net worth as the line, the retirement age as a solid rule, and a marker under the year each event **begins** (every event a year holds is still named in its read-out and hit area). A pure module the hook feeds as `netWorth`, with its assumptions on the same `retirementPlan` record: `incomeSource` (today's take-home grown by `incomeGrowthRateBps`, **or** gross `salaries` by age taxed by `workingTaxRateBps` — both kept, the source rule), `retirementTaxRateBps`, `cashRateBps`, `propertyRateBps`, and `debtAssumptions` per liability, kept here because a guess about a debt's future is not a fact about the account. **A debt payment is inside the budget's spending while working and on top of it once retired**; debts run on a real rate and a deflated payment. **Any change to it must keep its three tripwires green**: the yearly identity, the reproduction of `projectRetirement` with only a retirement pot, and a pot of `need` ending at zero.

**`resolveProjection({ plan, events, rows, budgets, expectedMonthlyCents })` is the hook's whole derivation as a plain function**, and the hook returns `resolveWith(plan, events)` beside its own result — the same books under a plan that is not in force. Every scenario row and every sensitivity row on the page is made by it, so a scenario differs from the current plan only by what it saved and never by a second derivation. `ScenariosPanel` shows the current plan and each saved scenario as rows of the same headline figures under `ScenarioCompareChart` (net worth by age, one line per plan: the current plan in ink, each scenario in its slot's colour), with Use / Update / Remove per row and "In use" where the live plan and events match one field for field. Its sensitivity table reruns the current plan with each of the three rates a point either way.

**The Retirement page has no month on it, and that is deliberate in a different way from the dashboard's.** The dashboard is undated because everything on it is as of today; this is undated because nothing on it is about a month at all. A stepper would suggest the projection can be walked back through, and a plan has no history — only a current shape.

## Spending reports (`src/hooks/useSpendingReport.js`)

The fifth cross-store hook, and **the only one whose subject is a span of months rather than an instant** (the sixth, `useGiving`, has a span too, but its unit is the year; the seventh and eighth, `useSavingsGoalEnvelopes` and `useEmergencyFund`, are back to an instant). Every other view answers a question about one period; a report cannot be, because the whole point of it is that one month is not evidence. Whether a category is overspent is a question about August; whether the estimate against it is *wrong* is a question about the year.

It reads the ledger and `toSections` and **nothing else**. Not assignments — what was put in an envelope is a decision, and a report is about what happened. Not balances, not the openings: money the household already had is not money it earned.

```
netSpent(b) = spent(b) − refunded(b)          ← what the category cost
income      = inflows naming no category
netCents    = income − netSpent = Σ inflows − Σ outflows   ← over the window
```

The store's refund rule carries through unchanged: an inflow **with** a category went back to it, an inflow **without** one is income. That identity is the tripwire in `useSpendingReport.test.js` — both sides count every inflow exactly once by different routes, and netting a refund off spending *and* adding it to income would inflate both halves of the headline at once, which is the one error a savings rate cannot survive.

- **A divided receipt is ranked by where its money went, not by the receipt.** Each part is a leg against its own category and its own bucket, which is the entire reason a household splits one: a shop filed whole under essentials hides what it actually spends on wants. Each row's drill-in shows the **part**, since that is what the figures above it add up to, with the whole named beside it (`wholeAmountCents`) so a $20 line against a $124 register row reads as an explanation rather than a contradiction.
- **Undated records are in no report.** `useEnvelopes` folds them into every cumulative sum because a balance must account for every dollar; here the axis *is* the month, so placing one would invent the history the migration refused to invent. They are counted instead — `undatedCount` / `undatedSpentCents` / `undatedIncomeCents` — and the page says so, because money missing from a chart has to be visible as missing. **`undatedCount` counts records, not legs**: a receipt divided three ways is one row on the register and has to be one here, while every cent of it still reaches `undatedSpentCents`. Records outside the window, future-dated ones included, simply are not in it: this is a report of a span, not a balance at the end of one.
- **`REPORT_RANGES`** — 3M / 6M / 1Y / YTD / ALL / Custom, inclusive of both ends, capped at `MAX_WINDOW_MONTHS` (120, the net-worth chart's ceiling and for the same reason). Five are counted back from the end month and run to the current one; **"custom" is the one that names both of its ends**, which is what lets a report cover a calendar year, or a year that has already finished. It is a sixth preset rather than a mode — everything downstream reads the window the same way whichever produced it — and it is the only range that reads the hook's third argument, as "all" is the only one that reads the ledger. Every path is guarded back to a window of at least the end month, or every per-month figure would divide by an empty list; a pair typed backwards hits that guard, though the page's two fields bound each other so it should not arrive.
- **The per-month average divides by the window, not by the months the category was active in** — that is what amortising *means*, and it is what makes a $1,200 annual premium comparable with the rent beside it. But it stops at the first month on the books (`averagedOverMonths`, `coverageStartPeriod`), or three months of records over a twelve-month window would understate everything fourfold and silently; the page prints the divisor when it differs. **Clipped at the far end too, by the calendar** (`coverageEndPeriod`, `coveredMonths`): a preset always ends at the current month and has nothing to clip there, but a custom window can be asked to run to December while it is still October, and counting two unlived months in the divisor would understate every figure on the page by a sixth. A month that has not happened is as empty as one nobody wrote anything down in, and for a better reason — so `PlanVsActualChart`, its table twin, `CategoryHistoryChart`'s trend and **`CashflowChart`'s net line** all withhold past `coverageEndPeriod` exactly as they withhold before `coverageStartPeriod`, while the plan's threshold is still drawn across both, since a standing figure neither began when the records did nor stops at today. The two ends are worded apart where the page explains the divisor, because "nobody wrote it down" and "it has not happened" are different facts and only one of them is fixable. Coverage is **global to the window, never per category**, or a category created last month would divide a one-off by one and report it as a monthly rate.
- **Rows are ranked by what was spent, not arranged by the plan.** The plan's order is answered twice already (Configuration sets it, the dashboard reads it); the question here has an order of its own, which is the whole reason a report is worth having. Each row carries its heading, so the arrangement is still readable — it is just no longer the axis. A category with nothing against it is not a row.
- `buckets` is the same four shares `usePlanHealth` reports off the *estimates* — essentials, fun, savings, retirement — read off the **books** instead, and that pair is the comparison. A category filed under no bucket (the Uncategorized sentinel, an id whose category was deleted) cannot be put in one of the four, so it gets a fifth segment rather than being dropped, or the split describes a smaller household than the headline does. The one asymmetry between the pair: `usePlanHealth` adds `pretaxContributionCents` to its retirement share, since a payroll deduction is money genuinely set aside; nothing here can, because a pre-tax deduction leaves no record in the books for a report of the books to find.
- **A transfer that moves no budget money is in no report**, not even in the undated count: paying a card is not an expense, and a report that counted it would say the household spent that money twice. One crossing the boundary **out** *is* spending against its category, exactly as the categorised outflow it replaces was. One crossing **in** is the single place this hook parts company with `useEnvelopes`, deliberately: there a withdrawal is money to assign because it can now be spent, here it is not income because the household did not earn it — draw $5,000 out of an emergency fund to fix a roof and this reports $5,000 of spending against what was actually earned, which is the month that really happened. The asymmetry is real rather than an oversight: the outbound half keeps faith with the shape the app already had, and the inbound half has no such precedent. `useGiving` keeps the same distinction, through its own `kind` test.
- `shareBps` returns `null` for a whole of zero or a negative one, and the page prints a dash — the same discipline as `percentChangeBps`.
- **`plannedCents` is the one figure here not read off the books**: every category's standing estimate, summed, including the categories that spent nothing — an estimate for a category that was quiet all year is still part of what the plan set aside, and dropping it would make the plan appear to shrink in exactly the months the household underspent. **Deliberately not `usePlanHealth`'s `plannedCents`**, which grosses the same sum up by `pretaxContributionCents`: a pre-tax deduction never becomes a transaction, so a plan that counts it drawn against spending that structurally cannot would show a permanent gap no amount of spending differently could close. `plannedWindowCents` is that figure times `averagedOverMonths` — the months the books cover, the per-month average's own divisor, for the same reason.
- **Each month also carries `buckets`, the same four-shares-plus-unfiled cut `buckets` reports over the window** — built in the one pass the rest of the hook already makes, since a second walk could disagree about the refund rule or about which month a record falls in. `BUCKET_SERIES` is the fixed list in the fixed order, **including the buckets a month spent nothing in**, because a stacked column colours a segment by its position and a list that dropped its empty entries would hand the same index to different buckets in different months. Each entry carries a `key`, since `bucket` is null for the unfiled segment and a null React key is a bug waiting for the next entry.

**The plan drawn against the books is `PlanVsActualChart`, the second chart on the page**, and it cuts the same months along a third axis: the cashflow chart is the household against itself, this is the household against its own plan. Neither answers the other — a month can be comfortably in the black and still be nothing like the plan it was supposed to be, which is the month a budget exists to catch. It is also the honest answer to the radar chart people ask for: which buckets are over and under, read on an axis that does not distort area.

- **The plan is a threshold, so it is the one dashed mark here** — `RetirementChart`'s target line is the only other one in the app. A category's estimate is standing, the same figure in every month, so the plan's total is a flat line rather than a series with a shape; a second set of columns would invite reading it as data that moved, and a flat *solid* line would be in the same visual language as the grid. `scaleFor` **always leaves room for it**, or the one household the chart has good news for gets its threshold drawn off the top of the plot.
- **The column is stacked by bucket because a month over the plan is a fact and which kind of spending put it over is the reason** — the only part a household can act on. Four hues and a grey, `stackPaths`' sign rule as ever, so a bucket refunded more than it spent draws below the baseline rather than being clamped.
- **A month the books do not reach gets no verdict.** The window can reach back further than the ledger does — twelve months asked for against four months of records is the ordinary case — and those empty columns are months nobody wrote anything down in. Measuring them against the plan would report eight months of perfect discipline nobody lived, which would be the most flattering lie on the page. `coverageStartPeriod` is what withholds it, in the read-out, in the aria label and in the table twin alike. **The threshold is still drawn across them**, because the plan is standing and did not begin when the records did; it is only the claim about a *month* that is withheld — the same distinction the per-month average makes when it divides by the months the books cover.
- **A plan of zero is a plan nobody has written, not a plan to spend nothing**, so no line is drawn and the page says so with a pointer to `/plan`. A line along the baseline would read as a plan every month overshot.
- Income is deliberately not on it. It is the chart above's subject, and a second series on a second scale is the one thing a reader must never be asked to do.

**`src/bucketTones.js` is the one place a bucket's colour lives**, read by `PlanHealthSummary` (the plan's own split), `ReportSummary` (the same split off the books) and `PlanVsActualChart`. The whole value of those three drawing the same four shares is that a reader carries the colours between them, and a second copy of the map would eventually disagree without anything looking wrong in review. Three forms — `swatch`, `fill`, `text` — and **each holds whole class names, never a token to be interpolated**: Tailwind's scanner reads source for complete class strings, so a `` `fill-${colour}` `` compiles against some other file's literal and vanishes the day that file changes. `text` is only ever safe on `text-figure`, where `azure`'s 4.1:1 on `panel` clears AA and nowhere below it.

**The page has one control and it sets the window**; everything moves with it together, including the divisor under every per-month figure. Five of its six options answer "how far back" and run to the current month, so the last column is usually a month still in progress; the sixth reveals a **From** and a **To** month and names both ends, which is the report a preset structurally cannot give — a calendar year, a tax year, a year already finished. It is still one control and not two: a preset derives both ends and ignores the pair, and the pair answers for both ends while it is in force. The two month fields are **kept rather than cleared** when a preset is picked back up, the switched-away-from rule, and each bounds the other so the window cannot be typed backwards. There is deliberately still no end-month *stepper*: walking the window back one month at a time is a different gesture from naming the window, and the presets already do it from the other end. **The chart and the table cut the same books along different axes** — the chart is the time axis, the table is the category axis over the whole window — and neither can answer the other's question.

`SpendingByCategoryTable` colours an average above the plan's estimate in `vermilion-ink`. **This is not a second definition of trouble contradicting the envelope view's one rule.** There the rule is `available < 0` and nothing else, because a category carrying money forward can exceed its estimate in one month by design. An average over the whole window removes exactly that defence — there is nowhere left for it to have carried from — so it says the estimate is wrong, which is a statement about the plan rather than about the envelope.

**Every row also carries `monthly` and `transactions` — the same window, one category deep** — for the drill-in (`CategoryDetailPanel`, drawing its chart through `CategoryHistoryChart`). The category's **name is a button**, not a heading, and clicking it opens the panel beneath the table rather than navigating away, because the ranking is still the context the reader picked that category out of; the same click closes it, so the row stays the one control. Both are built in the one pass the rest of the row already needs, never a second filter over the ledger: `monthly` is `months` mapped to that category's own `{ spentCents, refundCents, netCents }`, aligned index-for-index the way `series` is, so a month the category was silent in is a real zero rather than a gap; `transactions` is every dated, in-window record that fed the row, newest first. A second, independent filter here could disagree with the ranking about which window a record falls in or about the refund rule, and the two would drift apart silently — reading the row instead makes that impossible. `ReportsPage` owns which row is open (`selectedBudgetId`), not the table, because the selection has to survive the range control moving the window out from under it — a row can drop out of `rows` entirely when it did, and the page resolves the selection against the current rows rather than trusting it still names one.

## Giving (`src/hooks/useGiving.js`)

The sixth cross-store hook, and **the only one filed by calendar year**. Everything else here is filed by month, because a month is what a household plans in — but a deduction is claimed on a return, a return covers a year, and a goal that reset every month would be twelve different promises. Hence `YearStepper` beside `PeriodStepper`: same idea, different unit, and neither is a mode of the other. The year comes off each gift's own transaction date (`toYear`), derived and never stored, exactly as a period is.

**The ledger drives the join.** A tag whose transaction is gone contributes to nothing rather than to a figure with no row behind it, which is what makes the cascade in `deleteTransaction` a tidying rather than a correctness fix.

```
given(y)      = Σ tagged outflows dated in y  −  Σ tagged inflows dated in y
deductible(y) = the same sum over min(deductibleCents, amountCents)
```

- **A tagged inflow is money back from the organization and it subtracts** — the ledger's refund rule, applied to the one thing a returned donation changes here: it cannot be claimed in the year it came back. The row is marked `returned` and its deductible cell is not editable, because the sign belongs to the ledger and the way to restate one is to untag it.
- **The deductible portion is clamped to the gift, and the clamp is reported rather than repaired.** An amount edited down on the register leaves the stored figure out of date, not wrong — put the amount back and it means what it said again — so the row carries `statedDeductibleCents` and `clamped` beside the clamped figure.
- **An undated gift is in no year**, the same discipline the spending report applies to months: counted (`undatedCount`, `undatedTotalCents`) and said out loud, because money missing from a total that is going on a return has to be visible as missing.
- **A divided inflow is never income.** Naming no category is what makes an inflow earnings, and an inflow divided between categories names several — so it is refund all the way down, the same test `useSpendingReport` applies.
- **A share-of-income goal is a share of income *recorded*, not expected** — inflows naming no category, the report's own definition — so the target grows through the year, which is what stating a goal that way means. A refund is not income and is not part of what a tenth is a tenth of. `shareOfIncomeBps` is the same figure with no goal involved, and is what most households are actually asking.
- **`byRecipient` lists every organization, including the ones given nothing this year**: it is the list the page manages, not a ranking of the year's activity, and one that vanished in January would read as deleted. Gifts whose organization was removed get one unfiled bucket rather than a row each, because the parts have to add up to the total above them.
- **Nothing here is a tax calculation.** No limits, no carry-forward, no comparison against the standard deduction — those are questions about a whole return, and a figure that looked like an answer to them would be trusted as one.

`DonationList` owns the giving facts and the register owns the money facts: the organization, the deductible part and the receipt are edited on the row (blur for the figure, change for the select, as `TransactionRegister`), while the amount, the date and the description are read-only with a link to the register. **Untagging removes the statement, never the money** — the outflow still happened. `AddDonationModal` writes twice, ledger first, and **checks the giving fields before either write**, so the money is never the write that lands alone; the bound only it can check ("no more than the gift") lives there for the reason above.

## Savings goals (`src/pages/SavingsGoalsPage.js`, `src/components/SavingsGoalList.js`)

Medium-term saving in the envelope shape: a goal accumulates what is assigned to it, period by period, and `SavingsGoalList` reads like `CategoryLedgerTable`'s cousin — the target, what has accumulated, this period's contribution, what is left. The contribution is edited **on the row**, commit on blur, the contract `CategoryPlanner`'s estimate cell keeps: a blank is zero (the row the store prunes), a refused figure goes back and says why *under* the row rather than beside it, so a rejected edit does not change the width of a column the eye is reading down. `COLUMNS` drives the header and the error row's `colSpan` together, `TransactionRegister`'s rule, and one column names itself off the period because what was assigned is a figure *for* a month while the target and the balance beside it are standing facts. `GoalMeter` is `TallyGauge`'s ticks with the tone reversed — full means funded — local for the same reason `FundedMeter` and `GivenMeter` are, and pointedly not a call to either of those.

**The page has no stepper, for the dashboard's reason**: it answers where each goal stands right now, not a month to walk back through. It also carries a **read-only** reading of "to be assigned", because a goal competes with every category for the same unassigned dollar and that figure has to be visible where the competition happens — read-only because assigning it is `AssignIncomeModal`'s job and there is one door into that pool, not two.

**`AssignIncomeModal` funds categories and goals off one submit, against one shared pool.** The live "remaining to assign" counter sums both prefixes (`assign:` and `goal:`) out of one `FormData` read, so a dollar typed into the wedding fund leaves the counter exactly as a dollar typed into groceries does — which is the honest reading, and would not be if goals had a form of their own. A goal's **Fill** sets the period's contribution to whatever is left to reach the target outright, not to a monthly estimate: a goal has no per-period figure to top up to, which is what distinguishes it from a sinking-fund category. Two stores mean this cannot be one atomic write, so **every figure on the form is validated before either call runs** — the same reason `AddDonationModal` checks the giving fields before touching the ledger. If the budget write lands and the goal write is then refused, the modal stays open with the error; that is the residual the two-store shape cannot design away, and it is why the all-or-nothing batch rule inside each store matters.

## The emergency fund (`src/hooks/useEmergencyFund.js`, `src/components/EmergencyFundPanel.js`)

The **eighth** cross-store hook, and the join it owns is between the two halves of the app that had never met: the plan says what a necessary month costs, the balance sheet says what is in the savings account, and an emergency fund is a statement about both at once.

```
monthlyEssentials = Σ plannedCents of every category counting as essentials
derivedTarget     = monthlyEssentials × monthsCovered
target            = derivedTarget, or the typed figure where that is in force
counted(a)        = valueCents(a), or min(part set aside, valueCents(a))
held              = Σ counted over the ticked accounts, at useNetWorth's figures
remaining         = max(0, target − held)
```

- **The essentials figure is `usePlanHealth`'s, not a second sum.** That hook already resolves which bucket a category actually counts as — the question needs the group beside the category, and `toSections` has done it once — and the whole value of deriving the target from the plan is that this figure *is* the one the plan's own split reports above it. Two sums over the same records would eventually disagree about a category whose group moved, and the page would show a fund that did not match the share printed over it.
- **Pre-tax retirement money is not in it, and that is a property of the bucket rather than a rule here**: `usePlanHealth` grosses `pretaxContributionCents` onto the *retirement* bucket, and essentials never sees it — a 401(k) deduction is not a bill that still has to be paid when the income stops.
- **What is held is `useNetWorth`'s valuation and never a second reading of the accounts**, the rule `useRetirementProjection` keeps for the ticked retirement accounts: a savings account reconciled by hand counts at the figure the household entered, one the ledger answers for counts at the books' own arithmetic. One month of window, because all it needs is what each account is worth today. Signed, so a debt someone chooses to tick subtracts, on the one sign convention the balance sheet uses everywhere.
- **Two readings of the same money, deliberately.** `fundedBps` is the share of the target that is there; `monthsHeldBps` is how many months of essentials it would actually cover, which is the sentence a household asks the question in — and it survives a target of zero, which is the ordinary state of a plan nobody has written estimates into yet. Both are `null` rather than zero where there is nothing to be a share of, the `percentChangeBps` discipline, and the page prints the month count as its headline for exactly that reason.
- **Choosing to type a figure and typing none is a target of zero, not a quiet fall back to the derivation.** The household has just said they want to state the figure; answering with the one they switched away from would hide that the field is still empty. The derived figure is still *reported* while the typed one is in force, and the other way round, because the panel shows the answer not chosen beside the one that is — which is the only thing that makes keeping it worth anything.
- Nothing here writes anything, and nothing reads it back. The fund moves when the plan moves or when a statement is entered, which is the whole argument for deriving it.

**The panel is on `/plan`, full width below both columns, and open rather than folded away.** Full width because it joins the two columns — the target comes out of the left-hand column's estimates and the balance out of the right-hand column's accounts, `BalanceHistoryPanel`'s placement and its reasoning. Open, unlike the three panels beneath it, because those are opened to set something up while this carries a figure meant to be met in passing, and a buffer nobody is reminded of is the one most likely to be quietly spent. Both figures commit on **blur**, the contract every panel outside a modal keeps, and each input is keyed on the stored value so a rejected edit — or one made on another device — re-seeds it.

## The dashboard (`src/hooks/useDashboard.js`, `src/hooks/useNextPaycheck.js`)

`useDashboard(period)` joins `useEnvelopes` to `toSections` — the envelope figures, arranged the way the plan arranges them. Rows carry `availableCents`, `budgetedCents`, signed `activityCents`, `targetCents` (the standing estimate) and `goalCents` (the balance the category is saving towards, set on Configuration). **`goalCents` is `null` for a category with no goal — which is most of them, and all of the catch-alls** — and `null` renders as a dash rather than as $0. The same rule carries into the subtotals: `sumRows` adds up the goals that exist and returns **`null` when there are none**, so a band with nothing being saved for leaves the column blank instead of reporting a goal of zero. **Every envelope row lands somewhere** — categories under their group, the Uncategorized sentinel and orphans in `otherRows` — which is what lets `totals` be compared against the headline figures. A row is dropped only when all three summed figures are zero — available, budgeted and activity; a goal is never one of the three, since a category saving towards something it has not been given yet is still nothing on the books.

**Each row also carries `funding`, a reading of its own figures against its estimate** — `src/fundingStatus.js`, a pure module like `paySchedule.js`. Five readings: **overspent** (`available < 0`, which always wins), **underfunded** (what is left will not cover what the estimate still asks this month: `max(0, estimate − net spent) − available > 0`, and that gap is `shortCents`), **on track** (the rest of the month is covered — including a category that spent past its estimate and still holds money, since the plan has nothing left to ask of it), **well funded** (the rest of this month *and* a further month's estimate, or a goal reached), and **no estimate**, which gets no colour because there is nothing to be short of. **This is not a second definition of trouble** — the Available figure still goes red only below zero — it is a reading against the plan, the `SpendingByCategoryTable` distinction. `CategoryLedgerTable` maps it to red / yellow / green in a **Funding** column beside the name (the word always present, the shortfall named, a left stripe repeating the colour), with a key and a "N categories short by $X" line above the table off `useDashboard`'s `shortfall`. `FUNDING_TONES` there holds whole class names, `bucketTones.js`' rule. The panel's header also carries **Assign income**, the same `AssignIncomeModal` the register opens, since funding a category is the act this panel most often prompts.

`CategoryLedgerTable` drives both its header and its body cells off one `COLUMNS` array, so the two cannot disagree about how many columns there are. **The Available figure is also the control that moves it** — it opens `MoveMoneyModal` on that category, with a general door beside it in the panel's header. The figure rather than the row's name, because the money is the subject here and not the category (the name-as-button idiom belongs to the reports page, where the name really is what is being opened), and no new column either way, which would widen every row to carry a control used on one of them. **The direction is read off the row's funding and stated on the button**: a row that is short — overspent ("Cover …") or underfunded ("Fund …") — seeds as the destination with `shortCents` already typed in, and with **"to be assigned" as the source whenever the pool can cover it** (otherwise the source is left blank, since which neighbour gives something up is not the app's call); any other row seeds as the source. It belongs on the dashboard rather than on the register for the reason the to-be-assigned bar does not: what an envelope *holds* is a question about the plan and this page is where that question is answered, while the register is what actually happened. **There are four of them — available, budgeted, activity, goal — and `targetCents` is deliberately not drawn**, even though `useDashboard` still puts it on every row for whoever wants it. The standing monthly estimate is plan-level detail: it is set on Configuration and read there, it is the same figure in every period, and a dashboard is the at-a-glance page. Available leads because it is the figure the user acts on, budgeted and activity follow as the two things that moved it this month, and the goal sits last, away from the figures that come from the books.

**`ReconciliationList` is handed only the accounts the budget spends through** — `DashboardPage` filters `useAccountBalances`' rows on `spendsThroughBudget` before passing them. An off-budget holding is reconciled from the Net worth page, where its balance is actually used; nothing on the dashboard is assigned out of one, and its panel is about what the budget can spend. The balance on each row is derived and the reconciliation date beside it is not, which is exactly why the two share a row: a derived figure is only worth trusting as far as the last day someone confirmed it matched the bank.

`useNextPaycheck(today)` is the join between the stored schedule and `src/paySchedule.js`, which is the calendar arithmetic as a pure module — no React, no colour, no wording beyond the one phrase both readouts share.

**Two families of schedule, and neither is a variation of the other.** An *interval* cadence (weekly, fortnightly, a custom day count) is the closed form `next = lastPaidOn + k × days` for the smallest `k ≥ 1` with `next ≥ today`: at least one period on, so recording today's pay does not point at today, and never in the past, so a schedule nobody has updated in months still names a real date. A *monthdays* cadence (twice a month, monthly) has no payday to step from at all — it is named days of the month, clamped to the month's length, so `31` is the last day whatever the month is. A day count cannot express it: twice-monthly pay is 13 days apart in February and 16 in July, and a "15.2 day" period drifts off the calendar within a quarter.

**A monthdays payday landing on a weekend is paid the Friday before**, which is what nearly every payroll does; bank holidays are not accounted for, so a payday beside one can read a day late. The rule is never applied to the interval family — those are anchored on a real payday, so every step of seven or fourteen days lands on the same weekday it did. Shifting means a month's paydays are **not all inside it** (a payday on the 1st can be paid at the end of the month before), which is why the search window starts a month early and why the candidates are sorted and de-duplicated after shifting rather than before — two days can clamp or shift onto one date, and one payday is one payday.

`describeSchedule` is the single phrase for what a schedule *is* ("every 2 weeks", "on the 15th and the last day"), shared by the dashboard tile and `PaySchedulePanel` so the two cannot describe one schedule differently. On the panel **the cadence comes first and decides what else is asked**, since neither family's fields mean anything under the other; it is also the one control there that commits on change rather than blur, because there is nothing to half-type.

## UI conventions

Tailwind with **the Grove** palette (parchment, canopy green, the mascot's orange) and a dense type scale in `tailwind.config.js`. Take new colors from there — **never raw hex or default Tailwind colors** (the one exception is the Elder's own artwork, below).

**Every colour token is a CSS variable, declared twice in `src/index.css`** — on `:root` (light) and under `:root[data-theme="dark"]` — as bare RGB channels, so opacity modifiers (`border-vermilion/60`) still work. A component names a role, never a mode; adding a colour means adding it to **both** blocks, and a text pair has to clear 4.5:1 on every surface it sits on in each mode. The token names predate the two modes and are kept: `ledger` / `panel` / `panel-raised` / `edge` (page, cards, raised bands, card hairline) carry `chalk` / `chalk-soft`; `sheet` / `sheet-alt` / `band` / `rule` (data rows, zebra, subtotals, row hairline) carry `ink` / `ink-soft`. In both modes the two surfaces share a lightness, so the pairs are the same colour today — keep using the one named for the surface anyway. The header is the one surface that does not follow the page: `canopy` with `on-canopy` / `on-canopy-soft`, `coin` for the active-tab underline, and `on-canopy-rust` for the one warning that sits up there, the unsent-edits badge. **A tab is its label and the underline, nothing else** — there were coloured family dots beside the labels, and they came off because five of the eight tabs shared one colour, so the mark distinguished almost nothing and read as decoration. `action` / `on-action` is the primary button — green, and deliberately **not** `azure`, which is a figure, link and bucket colour beside `verdant` on the plan's split. `vermilion-ink` is destructive actions on rows. **The mode** comes from `useTheme` (`src/hooks/useTheme.js`): a `theme` key holding `"light"`, `"dark"` or `null`, where `null` follows `prefers-color-scheme` live; the header's "Dark mode" toggle pins one. It is a hook rather than a provider because it is a preference about the screen and nothing in the maths may read it — and for the same reason the key is **read bare, outside `src/storage.js` entirely**. It is deliberately absent from `STORE_KEYS`: a mode put through that seam would be namespaced per account, pushed to the server, cleared on sign-out, and written into the books file on the desktop — and `booksFile.js` *refuses* an unknown key rather than dropping it, so an export carrying a `theme` would fail to import. It survives a sign-out, which is right for a fact about the screen.

**`public/theme.js` makes the same decision before first paint** so a dark reload does not flash parchment — change one and change the other, since the two read the same key the same way. **It is a file rather than an inline block, and that is a CSP decision**: neither policy allows `unsafe-inline` for scripts, so an inline version would have to be named by its sha256 in *both* `vercel.json` and the shell's `contentSecurityPolicy()` — and that hash could not be taken from the source, because CRA's build runs index.html through html-webpack-plugin with `minifyJS` on, so the bytes the browser hashes are the minified ones. Served from the app's own origin, `script-src 'self'` already covers it in both and there is nothing to keep in step. It must stay **blocking** — no `defer`, no `async`, no `type="module"` — or it runs after the first paint and the flash comes back.

`font-display` (Young Serif) for the app name and the page `<h1>` only, `font-sans` (DM Sans) for structure, `font-mono` (IBM Plex Mono) for figures, on `text-label` / `text-row` / `text-figure`. Currency goes through `formatCents`; columns of figures get `tabular-nums`, and a large standalone figure does **not** (equal-width digits make a hero number look loose). `formatCompactCents` is the axis-tick form ("$42.5K"), hand-rolled rather than `Intl`'s compact notation so the browser and the test runner cannot disagree. `CURRENCY` and `CURRENCY_LOCALE` are pinned together.

**The Elder** (`src/components/Elder.js`) is the mascot: one head, four moods, and the mood is a reading of the books, never decoration — `content` when everything is assigned, `pondering` when money is waiting for a job, `concerned` only for the app's one definition of trouble (below zero), `pleased` for a goal reached. Callers pick the mood from the same rule as the figure beside him, he appears at most once per screen and never over a figure, and he is `aria-hidden` unless he is the only carrier of what he means. His colours are written out in the file because he looks the same in both modes. Today he is in the header, the dashboard's available-to-budget tile, `ToBeAssignedBar`, and `AddTransactionModal`'s nothing-to-file-against state.

**The four net-worth series colours (`verdant`, `invested`, `property`, `vermilion`) are the one part of the palette chosen by measurement, not by eye** — a stacked chart is read by telling its bands apart. They are checked all-pairs and against `panel`, **in both modes**, by CIEDE2000 under normal vision and simulated protan/deutan (Machado 2009, full severity): worst pair 12.4 in light, 12.6 in dark (Gotham's four scored 8.5 by the same measure). `invested` and `property` differ in lightness as well as hue, which is what carries them under protanopia. The legend, the direct end-label and the page's table view stay load-bearing regardless. **Changing one of the four means re-validating all four, in both modes** — and the plan's bucket colours (`azure`, `sulfur`, `verdant`, `invested`) were checked the same way, which is why light-mode `azure` is a teal rather than a blue.

The chart now draws one series *per account*, and **the number of accounts moves the ramp, never the palette**: colour still says which band, and lightness says which account within it. `styleSlices` steps each band's hue toward the surface by position (`SHADE_FLOOR` 0.5, spread evenly however many are in the band) and same-hue slices are stacked adjacent so each band reads as one ramp. Hue count is what makes a stacked chart unreadable, so a fifth hue is never the answer. The shades are drawn as `fillOpacity` on the band's Tailwind `fill-*` class rather than as mixed hex, which is also why each column gets a `fill-panel` backing rect first — without it the grid hairlines show through a dimmed segment as stripes across the money.

Shared components in `src/components/` — read the file before reusing one. Rules that are not visible from the call site:

- Every page starts with `PageHeader`, whose title is the page's only `<h1>`.
- `Button` `variant` names the surface: `primary` / `outline` / `danger` on the page and its cards, `row` and `row-action` inside data rows, and `canopy` on the header band. `row` is bare text that turns red on hover — it is what "Remove" wears, and the hover colour is the warning; anything non-destructive takes `row-action`. **`canopy` is the one variant whose colours do not move with the mode**, because the band it sits on is the same green in both; `outline` is wrong there twice over, since `edge` and `panel-raised` are the chrome's own greys and read as a smudge on green. Everything in the header wears it — the mode switch, and `AccountControl`'s sign-out and sync buttons.
- `TallyGauge` treats a non-positive `max` as a zero ratio, so **callers must suppress it rather than pass one**. `SplitGauge` draws nothing at all from all-zero weights, so the same rule applies to it. `RetirementOutlook`'s `FundedMeter`, `GivingSummary`'s `GivenMeter`, `SavingsGoalList`'s `GoalMeter` and `EmergencyFundPanel`'s `BufferMeter` are the same ticks with the **tone reversed** — full means funded, or the goal met, not spent out — and each is local for exactly that reason: one component reading both ways would be a trap for whichever caller came next, and that is also why the second is not a call to the first.
- `SegmentedControl` and `SourceChoice` look alike and are not interchangeable. `SegmentedControl` is a strip of `aria-pressed` buttons for a choice about **what is on screen** — nothing it does reaches a store, so every option stays in the tab order and comparing them is one click. `SourceChoice` is radios for a question the **plan keeps an answer to**, where the answer not chosen has to stay visible beside it.
- `SourceChoice` is the radio pair for a question with two legitimate answers, used twice on the retirement page, once on `GivingGoalPanel` and once on `EmergencyFundPanel`. **No two uses may share an option label** — "a figure I enter" twice over is two radios with one accessible name between them, so they read as "a balance I enter", "a yearly figure I enter" and "a target I enter", and the fund's derived option names what the figure *is* ("months of my essentials") rather than how it arrives.
- Help text under a field goes **outside** the `<label>`, tied to the input with `aria-describedby` (see `RetirementAssumptionsPanel`'s `Field`). Nesting it folds a sentence of guidance into the field's accessible name, so nothing can find the field by its name and a screen reader announces the whole paragraph on focus.
- **`src/payeeSearch.js` is the payee search as arithmetic over strings**, a pure module with no design opinion in it like `paySchedule.js` and `chartAxis.js`. `searchKey` folds case and punctuation; `matchPayees` returns `{ matches, moreCount }` ranked **exact › prefix › word-boundary › substring** then alphabetically, capped — `moreCount` exists so a truncated list never looks like a complete one. An **empty query is "anything", not "no matches"**, in the order it was handed (see `orderPayeesByUse`, which reads recency off the ledger rather than storing a `lastUsedAt` that could disagree with it).
- **`src/chartAxis.js` is the arithmetic behind a column chart over months, and it carries no design opinion** — no colour, no layout, no wording, no ARIA. `axisTicks` (which **always includes zero**, guards an empty domain, and rounds to figures people say), `axisLabels` (counted **back from the most recent**, so the right edge is always named), `columnPath`, `stackPaths`, `barWidthFor`, `radiusFor`, `movingAverage`, `lineRuns`. `NetWorthChart`, `CashflowChart` and `PlanVsActualChart` all draw through it; what stays in a chart file is what that chart *means* — its frame, its series, and how it says what it is showing. `stackPaths` is the one rule the two share outright: **a value is drawn on the side its own sign puts it**, which is what lets the spending band be one series and a month of net refunds draw upward, and what guarantees the stack's two extents add to the net so the line is always inside the column.
- **A dashed line is for a threshold, never a grid.** The grid hairlines are solid everywhere for that reason; `RetirementChart`'s target line and `PlanVsActualChart`'s plan line are the only dashed marks in the app, because each is the figure the data beside it is meant to be measured against. A trend line is **solid**, since it is data.
- **A column is a sum and a line is a claim.** A month the books do not reach draws its columns at zero either way — that is what was spent, which is nothing — but a *line* through it says the household broke even, which is a statement about a month nobody recorded or has not yet lived. So `CashflowChart`'s net line and `CategoryHistoryChart`'s trend both break outside the coverage window rather than spanning it, and the cashflow chart's end dot and direct label move back to the last month the line actually reaches: a figure floating past the end of a broken line would be the one the eye lands on, naming the single month the line declined to describe.
- **`movingAverage` is the trend under the noise, and `lineRuns` is what draws a series with gaps in it.** The average is **trailing**, not centred, because the right-hand end is the month the reader came for and a centred average has nothing to say about it; the lag is the honest cost and shows as the line sitting behind a turn. It returns **`null` until the window fills** rather than averaging whatever is there so far — a "three-month average" computed from one month is that month, and a line that traced the data and then peeled away would read as the trend changing when all that changed is the divisor. `lineRuns` **breaks the line across a null rather than spanning it**, the same refusal `useNetWorth` makes when it will not propagate a snapshot backwards, and gives a run of one point no line at all.
- **`CategoryHistoryChart` carries the only trend line, and it is three-month trailing.** The columns answer what the category cost in March; the line answers the question a drill-in is actually opened with, which is whether the habit is shifting — and a column chart is close to useless for it, since spending that climbs ten percent a year and spending that is flat look identical under one month that held a party. An average rather than a fitted line, because a regression over twelve points states a confidence this data has not got, and because a household can check an average against the three columns above it. **It is taken over the months the books cover, not over the window** (`coverageStartPeriod`, passed down through `CategoryDetailPanel`): averaging through the empty months before the ledger starts draws a line climbing out of the floor on every category the household owns, which is the exact misreading a trend line exists to prevent. Below four covered months there is no line and no legend entry for one.
- Percentages that are shown together go through `apportion` (`src/utils.js`), which splits by largest remainder — three independently rounded shares add to 100 only by luck.
- **`AccountPicker` is the one list for ticking which accounts count towards something**, shared by `RetirementStartingPoint` and `EmergencyFundPanel`. The same question twice, and the part worth not writing twice is what a row says about **where its figure came from**: a holding last valued in March is being counted at March's figure, and two panels wording that differently would be two panels a reader could not check against each other. Values are `useNetWorth`'s and nothing on a row is editable but the tick — an account is corrected where it is owned, on the balance sheet. `holdingsFirst` is the only thing the two callers disagree about, and it is a question about which accounts the panel is *usually* about rather than about the data: retirement money is off budget, a buffer is most often an ordinary savings account.
- **`PayeeField` is the one control for naming a payee**, shared by the entry form and every register row so the two cannot disagree about what a match is or what the keyboard does. A **real combobox** rather than an `<input list>`: a datalist cannot be styled to either surface, cannot carry a second line on an option, cannot offer "create this one", and matches differently in every browser. The **second controlled control in the app** after `SplitParts`, for its reason — the set of options changes as the user types. Two faces like the register's money cells (the payee at rest, what is typed under the caret), and **focus selects**, or the first keystroke inserts into the middle of the old name. It **never creates anything itself**: `onCommit` hands back either a `payeeId` or a bare `name`, because *when* a payee comes into being is the host's rule — the form holds a draft until submit so an abandoned form leaves nothing behind, a register cell has no submit and creates on blur. `onType` reports every keystroke for the form, whose submit can be clicked from a field that was never blurred. Three details are load-bearing: the list is **fixed-positioned** (the register's table scrolls on one axis, which clips the other), **Escape stops propagating** (a `<dialog>` closes on it), and **Enter is consumed while the list is open** (one keystroke must not both pick a payee and save the transaction). Nothing is active until an arrow key says so, so Enter means "what I typed".
- **A payee's default category seeds the entry form and never the register.** In the form it applies until the user answers the question themselves, tracked in a `chosenRef` — `AddBudgetModal`'s bucket-follows-group idiom. On a row it never applies: re-filing money that is already filed because a name was corrected is the thing this app does not do quietly.
- **`type="month"` is the one native date-ish input the app uses, and only for a period.** The reports page's custom window is two of them. It is not a breach of the rule below: that one is about money, where a number input refuses "$1,234.56" and reads back empty, while here the field's native value format and the app's own period format are the **same string** — "2026-03" — so nothing is parsed and a browser without a month picker falls back to a text box showing exactly the figure it wants. They are **controlled**, unlike every other form here, for `SplitParts`' reason one step down: each end bounds the other, so each field's limits are the other field's value, and nothing is being written to a store that could disagree.
- **No field that takes money is a `type="number"`, anywhere.** A number input refuses "$1,234.56" and "1,234.56" alike — the box looks filled and reads back **empty** — and it renders $78.40 as "78.4", so a column never lines up on its decimal point. Money fields are `type="text"` + `inputMode="decimal"`, and the figure is checked where it always was: at the store boundary, which is why dropping `min` / `step` costs nothing. The same goes for the rate fields, which people write with a "%". Only the ages and the pay-schedule day count are still number fields — a whole number with nothing to punctuate. **The two faces of a money field are `amountAtRest` / `amountEditing`** (`src/utils.js`): formatted at rest, raw under the caret. `amountField` is that pair wired to focus and blur, spread onto fields read back on **submit** — the balance grid, the monthly update, the assign form, which sit beside formatted figures and must not disagree with them. A field that commits on **blur** owns that event and writes its own handler (`TransactionRegister`, `CategoryPlanner`), since what goes back in the box after a refused edit is a question only that field can answer.
- The envelope view has **one** definition of trouble, `available < 0` — not a second rule about the estimate, which an envelope with carry-over can safely exceed.

`Add*Modal` forms are uncontrolled (`useRef` per field, read on submit), stay mounted, and toggle on a `show` prop. **Because they never unmount they must re-seed on open** — a `formRef` effect on `show` that calls `form.reset()`, clears the error, and re-applies defaults. Without it fields keep the previous entry and `<select>` `defaultValue` silently does nothing after first mount. `AssignIncomeModal` recomputes its live counter from `FormData` in one form-level `onChange` rather than holding state per row; its re-seed effect depends on `[show, period]` and deliberately **not** on the rows array. In `AddBudgetModal` the bucket select follows the group select — that is what "the group's default" means now — but only until the user answers it themselves, tracked in a `chosenRef` and reset on open: a choice already made is not a default.

**`MoveMoneyModal` is the one door to moving money between envelopes — and between an envelope and the pool.** "To be assigned" (`TO_BE_ASSIGNED`, in `src/contexts/constants.js`, never stored) is offered first on both sides; `moveBetweenBudgets` writes only the category side when one end is the pool, so moving from it *is* assigning and moving to it is assigning less, and the identity holds for the reason it always has. It is opened from a `CategoryLedgerTable` row or from the panel's header, and it writes through `moveBetweenBudgets` — one action, one write, and **no ledger rows at all**, because moving money between two envelopes is a change of plan rather than a movement of money. A modal and not a row of cells for `AddAccountModal`'s reason: a move is three interlocking answers that are only valid together, and the figure it is checked against (what the source actually has) is on neither row. Uncontrolled like every form here, with the live before-and-after read off `FormData` in one form-level `onChange` — `AssignIncomeModal`'s idiom, and for its reason: seeding from the derived rows would let this modal's own write echo back over what is being typed. **It states what each side will be left with and refuses nothing for it**: a move that leaves the source overdrawn is a real thing to want in the week before a paycheque, and the app's one definition of trouble says so the way it always does, in red — here before the write and on the row after it.

**`FixDriftModal` is the other half of `driftCents`**, reached from the Source cell of the `HoldingsTable` row that states the gap — noticing it and closing it are one thought, so they are one click, and a cell that already names the figure beats a new column every row would have to carry. What it writes is an ordinary inflow or outflow dated inside the statement's month; see the net-worth section for why that is not a fourth kind of record. `HoldingsTable` is otherwise still read-only: updating the month's figures is not offered there, because it already sits in the page header and a second button with the same label further down the same screen makes a reader stop and work out whether the two do the same thing.

**Four modals add or edit depending on one prop** — `AddGroupModal` (`group`), `AddAccountModal` (`account`), `AddOrganizationModal` (`organization`) and `AddSavingsGoalModal` (`goal`) — because each record is a handful of answers that are stated the same way whenever they are stated. The last of those depends on `[show, goal]` rather than `[show]` alone, since the page opens the same mounted modal on a different row without closing it in between, and seeds its target through `amountEditing` rather than a bare `fromCents` so a $1,250.50 target does not come back as "1250.5". What that costs is that the re-seed effect now seeds *from* something, and `seedFor` is where AddAccountModal keeps that in one place: the effect writes the fields through their refs, and the **kind and asset-class selects take the same seed as their `defaultValue`**, mirrored in state. Both unmount whenever a debt or a card is chosen, and a remounted `<select>` takes its `defaultValue` — so a class only written to the DOM comes back as Cash and quietly reclassifies a brokerage. For the same reason `handleChange` falls back to the **account's own** kind rather than the prop default, or a detour through the card option would turn a mortgage into an asset.

**`SplitParts` is the one editor for a division, and the one controlled form control in the app.** Shared by `AddTransactionModal`, where a receipt is divided as it is entered, and `SplitTransactionModal`, where one already in the ledger is divided or redivided — one editor because the arithmetic *is* the feature, and a second implementation of "the parts add up" is a second chance to get it wrong. It is controlled because the **set of fields is itself being edited**: every other form here has a fixed shape and is re-seeded through refs when it opens, which works precisely because `defaultValue` is only ever needed once per field. The host holds the parts in state and seeds them on open exactly as it seeds its refs. The money field keeps both faces all the same, formatted at rest and raw under the caret, with the selection made in a `queueMicrotask` — made before React writes the raw figure it would be collapsed by the swap. Parts are held as **typed strings**, not cents, because a half-written "12." is a real state on the way to "12.50". `describeSplitProblem` is the one wording for what is wrong with a division, with the figures in it that the store's own messages cannot have; both hosts check it **before** any write, since a transaction that landed and then had its division refused would be a receipt in the ledger filed under nothing. "Add a part" seeds the new row with whatever is still unplaced, which is the figure it almost always wants.

`SplitTransactionModal` is a modal rather than a row of cells for `AddAccountModal`'s reason: a division is several interlocking answers that are only valid together, so the whole of it commits at once — the all-or-nothing rule `setPeriodBalances` and `setPeriodAssignments` keep for a window of figures. **It edits the total too**, and has to, since that is the figure the parts are checked against. Its re-seed effect keys on `transaction?.id` and **not** the record: the ledger hands out fresh objects on every write, and depending on the object would wipe a division halfway through being typed the moment another device synced an unrelated row. The consequence, stated rather than worked around: **a split row cannot change direction**, because the column that flip is typed into is not a field on one. Undo, flip, split again — three steps for something rare, and better than a half-applied flip leaving the parts describing the other direction.

**The header carries "Add transaction" and "Transfer" on every page** (`QuickEntry` in `AppShell.js`), the second opening the same form on the transfer direction. The modal is **mounted only while open** there, unlike every page-owned modal: the header renders above every page and in suites with no stores, and a closed copy would put a second set of field labels on every page. `TransactionsPage` no longer has an Add button of its own for that reason — two buttons with one label on one screen — though the register's empty state still opens its own copy.

`AddTransactionModal` **opens on the accounts last used** per direction — the account the latest spending or income went through, the pair the latest transfer named — read off the ledger's order (`recentAccounts`), never stored; each account select is keyed on an open counter as well as the direction, because a mounted `<select>` keeps the `defaultValue` it first had and `form.reset()` returns it there. **"Save and add another"** keeps the direction, accounts, date and category, clears the payee, amount, note and any division, says what landed in a status line, and puts the caret back in the first field. **Add is first in the DOM and drawn last** (`flex-row-reverse`), because Enter submits through a form's first submit button and Enter has always meant "add and close"; which button was pressed is held in a ref set on click, since `SubmitEvent.submitter` is not reliable everywhere.

`AddTransactionModal` is the one entry point for all three directions — money in, money out and a transfer are one form with a toggle, not three modals. Three things about it are not visible from the call site: the direction is held in **state** (it decides which fields exist, and `form.reset()` cannot reach it, so the re-seed effect sets it explicitly); the form is **replaced entirely** by a pointer to `/plan` when there is no on-budget account or no category, since a form whose submit can only fail is worse than no form (that guard is why the re-seed effect has to tolerate a null `formRef`); and the category select is **keyed on the direction** so switching remounts it, which is what gives each direction its own default — the first category for money out, none for money in. Reusing the element would silently turn the next paycheque into a refund against whatever was picked for the last expense.

It has a **third** exception to "uncontrolled", beside the direction and the two accounts: the parts of a division, and the amount mirrored into state so the editor can say how much of it is still unplaced. The ref is still what submit reads, so there is only ever one answer.

On the transfer direction two further things hold. **It is the one form where an off-budget account is offered**, on both ends — elsewhere they are kept out because nobody logs each tick of a 401(k), but a contribution *into* one is precisely the event a household does know about. And the **two accounts are mirrored in state** alongside the direction, for the same reason the direction is: they decide which other fields exist, since only a pair that crosses out of the budget asks for a category. That category select carries a blank `Choose a category` prompt rather than defaulting to the first one — which savings category a contribution comes from is exactly what the app cannot guess — and submit refuses without it, which is the matrix rule the store is mounted too high to check.

`CategoryPlanner` edits four things on the row itself: the **name**, the estimate and the goal are uncontrolled and commit on **blur** (a rejected value — a blank or clashing name, a bad figure — is put back, since the rest of the app still knows the category by the old one), while the bucket select is **controlled**, because there is nothing to type and the choice commits on change. The name input is keyed on the stored name so a successful rename re-seeds it with what was actually saved, and the goal on the stored goal, which has two empty states to tell apart. **The goal cell sends the raw string, not cents** — blank and junk both parse to `null` and only one of them means "no goal", so the store is the one that reads it. Two figure columns on one row is also why the section grew a heading row: with one figure an aria-label was enough. Its unlabelled cells (the drag handle, Remove) are `invisible` copies of the real controls rather than hand-measured widths, and every fixed width — `bucketClass`, `figureClass` — is shared by the heading, the row and the drag overlay so the three cannot drift apart. Both are as narrow as their contents allow, because what they take comes out of the name, which is the only field on the row holding a phrase rather than a short figure.

`TransactionRegister` is the same contract at grid scale, plus six rules of its own. **The Payee column holds two fields stacked, not one** — the payee through `PayeeField` on top, the note under it — because the six fixed widths already come to 712px and the grid has to stay inside its container at 768px, which is the same arithmetic that put both ends of a transfer in the Account cell. A transfer names nobody and shows the note alone, as does every row written before payees existed; `nameOf` reads payee, then note, then "untitled entry". **Money in and money out get a column each**, never one signed figure — that is how a register has always told them apart, and it is also how the direction is *edited*: a figure typed into the other column moves the row across, so a misfiled paycheque costs one edit rather than a delete and a full re-entry. Both amount cells are keyed on the direction **and** the figure, so a commit to either remounts both and nothing is left behind in the column the row came from. **Clearing a cell is an abandoned edit, not a value** — a blank date does not un-date a record and a blank amount is not a transaction of nothing, so both put back what is stored. Amounts are **formatted at rest and raw under the caret**, through `amountAtRest` / `amountEditing` rather than formatting written in the file; `toCents` takes back whatever the field wrote, symbol and separators and all. And the row's current category and account **always have an option**, even one the form would not offer — an off-budget account, a deleted category, the Uncategorized sentinel — or the select would show its first entry and the row would look refiled by being looked at.

**A divided row breaks the column rule the other way.** Its category is not one answer but several and its figure is whatever those add up to, so neither cell can be edited where it sits — a part typed down on its own would leave the division short of the whole, and the store would refuse it every time. Both become buttons onto `SplitTransactionModal`, wearing the register's own cell styling (no rule at rest, a rule under the pointer, azure under the caret) so they read as the way that row's figures are changed rather than as something else; the column the row is not in is an inert dash, for the transfer's reason. Starting a division is the last option in the Category select (`START_SPLIT`) rather than a control of its own — it is an answer to the question that column asks, and there is no width on this grid for a seventh anything. `totalsOf` counts a divided receipt **once, at its whole**, since that is what came into the household or left it.

**A transfer row is the one that breaks the column rule, because it has no direction to change sides on.** Its direction is its pair of accounts, so it takes the Out column, its In cell is an inert dash rather than an empty input (a figure typed there must not turn it into an inflow), and **both of its accounts sit stacked in the Account cell** — the second prefixed "→" — rather than in a seventh column, which another `w-36` could not fit under the 768px ceiling above. Whether it has a category to file is not the user's choice either: only one leaving the budget comes out of an envelope, so the rest show a dash there too. Both rules read `insideBudget`, the predicate the form and `budgetLegs` ask, so no two screens can disagree about one row. `totalsOf` counts a transfer in **neither** footing — those are what came into the household and what left it, and a transfer did neither.

Two things about its layout are load-bearing. Cells draw **no rule at rest**, only under the pointer and as an azure box under the caret (the app's global `:focus-visible`): sixty underlines is a grid of noise over the figures the page exists to show, which is why `CategoryPlanner`'s always-on rule does not carry over to a table. And the table is `table-fixed` with a width on every column but Description — **but never a `min-width` on the table**, tempting as one is for narrow windows: Chrome counts a table's min-width against the *document's* scroll width even inside an `overflow-x-auto` box, so a floor wide enough to keep the columns apart puts a scrollbar under the whole page. Keep the fixed widths summing under the container at 768px.

Panels outside a modal that edit a store — `PaySchedulePanel`, `RetirementAssumptionsPanel`, `RetirementStartingPoint`, `GivingGoalPanel` — are uncontrolled too, commit on **blur** (a half-typed "1" on the way to "14" is a valid figure), and key each input on the stored value so a change made elsewhere re-seeds it. A value the store *rejects* changes nothing and so stays on screen to be corrected, with the message beside it. `BalanceHistoryPanel` is the exception that proves the rule: it is a panel, but it commits on **submit**, because a hundred and forty-four cells that each wrote on blur would be a hundred and forty-four writes for one pass over the statements. Its cells are keyed on account, month **and** the figure stored for them, so moving the window and saving both re-seed the grid while typing does neither.

## Testing

- jsdom 16 has no `<dialog>`; `src/setupTests.js` polyfills `showModal` / `show` / `close` and the `close` event. Guarded, so native support wins later.
- Tests seed pre-migration JSON into `localStorage` before `renderHook` and use the real `AppProviders`, exercising migrations and provider order rather than mocking them. **This still works, and that it does is the point of the migration's shape**: with no `AuthProvider` above them the storage scope is null, so a bare key is the real key and no network exists to mock. Nothing in the store suites had to change.
- `storage.test.js` covers the namespacing — that two accounts on one browser cannot read each other's books, that sign-out takes an account's books out of the cache and leaves the unscoped ones alone, and that an empty `[]` is not "books to import". Its last test **reads `src/contexts/*.js` and fails if a store's key is missing from `STORE_KEYS`**; it is the only test in the suite that reads source, because nothing else can catch that — the app works perfectly until the user opens it somewhere else.
- `AuthContext.test.js` mocks `../supabaseClient` and drives the provider and the gate. Note that **react-scripts sets `resetMocks: true`**, so a mock implementation defined at module scope is wiped before every test — stage them in `beforeEach` or they come back `undefined`. The session lookup is a promise resolved in an effect, so settle it with `await act(async () => {})` before asserting, or its state update lands outside act. Its **signing in by email** block asserts `signInWithOtp`'s `options` **whole**, the discipline this suite keeps for a stored record and for the same reason: those options are the entire security content of the call, so `shouldCreateUser` going missing is exactly the kind of regression nothing else would show as a failure. The two halves worth not losing are that an unknown address reports `{ ok: true }` **and** sets `pendingSignInEmail`, since a wording-only fix would leave the following screen distinguishable; and that the shell's call carries no `emailRedirectTo` **key at all**, staged by assigning `window.__hbDesktop` the way `storage.test.js` does.
- **`electronBooks.test.js` tests main-process code and lives in `src/` anyway**, which is the one placement in this suite that contradicts the rest. CRA pins Jest's `roots` to `<rootDir>/src` and does not allow that key to be overridden (`createJestConfig.js` lists what it takes, and `roots` is not on it), so a test under `electron/` is never discovered — it does not fail, it silently does not exist. It drives `electron/books.js` against **real files in a real temp directory**, because the atomicity being relied on is the filesystem's own and a mocked `fs` would only assert that the module calls `renameSync`. `jest.resetModules()` before each `require` is required: the module is a singleton over one file. What it pins down is durability — the debounce pair, the launch-time backup taken once, the quarantined unreadable file, and that a refused write stays dirty.
- `storage.test.js` stages a fake `window.__hbDesktop` and calls `resetStorageBackend()` to pick it up, which is the only reason that export exists — nothing in the app calls it, since the shell cannot change mid-session.
- `useSyncedState.test.js` is the old `useLocalStorage` suite plus the sync half: what the hook pushes, what it does with a change from another device, and that an unreadable remote document leaves the store alone rather than blanking it. It stages a `SyncContext.Provider` directly rather than standing up a real one.
- **Any change to the envelope maths must keep the identity tripwire in `dataModel.test.js` green** — nothing else catches a row-set or cascade regression. `expectBalanced` there is the invariant written out, **including the `goalRows` term**: `toBeAssigned + Σ available + Σ goal available` against `opening + cumIncome − cumSpent`. Drop the goal term and every goal assignment reads as money vanishing. Its `transfers` block asserts the same identity in **all four quadrants** of the matrix, which is the only thing standing between a change to `budgetLegs` and a transfer that quietly creates or destroys money.
- `SavingsGoalList.test.js` takes props and stages `onAssign` as a spy, the way `TransactionRegister.test.js` and `PaySchedulePanel.test.js` do: what it pins down is the row's editing contract — which figure a cell sends, and what it puts back and says when the store refuses one — not how the goals got there. The store end, the delete cascade, and the pool arithmetic are all in `dataModel.test.js`.
- Seeding the `transactions` key — or the legacy `expenses` key, which still folds in — also fires the day-one assignment seed; to test spend with no funding, write an empty `assignments` key too.
- Any test that writes a transaction must seed an **account** first: the store refuses one without an `accountId`.
- Modal regressions only appear across repeated open/close cycles, so drive them through a harness that mimics `TransactionsPage`. `AddModals.test.js` wraps `AppProviders` in a `MemoryRouter`, because the transaction modal links to `/plan`.
- Tests that assert a whole stored record must list **every** field — `reconciledOn` on an account, `goalCents` on a budget. Three broke when the first was added and three when the second was, which is the point.
- `fundingStatus.test.js` drives the funding rule as the pure function it is — every threshold named in cents. `DashboardPage.test.js`'s **funding** block checks the column's words through the real stores, that an underfunded row opens the move from the pool with the gap typed in, and that a shortfall the pool cannot cover leaves the source blank. The Funding cell is the row's **first** `cell` now, so a figure read by position is at `[1]`.
- `DashboardPage.test.js` renders the page through the real providers rather than mocking the hooks; it is what caught a column dropped from the table header and left in its body. Its **move** block drives the figure-as-button both ways — an overspent row opening already pointed at covering itself, a row with money to spare opening as the source — the before-and-after read-out, the write landing on both rows, and a refused move keeping the form open. The store end is `dataModel.test.js`'s own block, which is where the part that matters most lives: that the move is **one write**, so the sum across the two rows is unchanged at every point a reader of storage could look, and that the pool is exactly where it was afterwards. If a future change ever routes a move through the pool, that is what catches it. `NetWorthPage.test.js` does the same and drives the period stepper, since backfill *is* the stepper plus a modal that writes to the month on screen. Its **settling** block is there for the same reason one level up: the claim `FixDriftModal` rests on is that the correction is an *ordinary transaction*, so what has to be asserted is the row that lands in the ledger — whole, `splits` and all — and the gap closing as a consequence of it. Neither is visible to a mocked hook. It also pins down that a hand-valued holding has no gap to settle at all, because growth is not a disagreement about the books.
- `BalanceHistoryPanel.test.js` takes props too, and drives the grid rather than the store: what it pins down is the blank-versus-zero contract — a typed month becomes an `amountCents` entry, the months around it stay blank ones that clear, and the figure carries forward without a record being invented for it. The store end of that, including the all-or-nothing window commit, is in `dataModel.test.js`.
- `TransactionRegister.test.js` takes props and stages `onChange` as a spy, since what it pins down is the cell contract: which patch a cell sends and what it does with the answer. `TransactionsPage.test.js` runs the same edits through the real providers, because an edit is only worth anything if it lands — that is where the direction flip, the refused flip, and the legacy-row correction are checked end to end.

- A `<dt>` does not take its accessible name from its content, so `getByRole("term", { name })` finds nothing. Reach a figure through its term's text and `nextElementSibling`, scoped to the region — most of these labels deliberately also name the input that sets them.

Money and rates are textboxes, so `getByRole` wants **`"textbox"`**, `toHaveValue` takes a **string** ("$12,500", or `""` for empty, never `null`), and a rejected figure can be tested with a word again.
