# TESTING.md

Everything about testing this app: the environment gotchas and the seeding rules that bite on any change, the five tripwires that hold the maths together, and which suite covers what. **Read this before writing or changing a test, so a new one does not re-test what an existing one already pins down from the right side.**

## Environment

- jsdom 16 has no `<dialog>`; `src/setupTests.js` polyfills `showModal` / `show` / `close` and the `close` event, guarded so native support wins later.
- **jsdom 16.7 ships no `crypto` at all and no `TextEncoder`/`TextDecoder`**, so nothing in `booksCrypto.js` runs without both polyfilled. `src/setupTests.js` installs `node:crypto`'s own `webcrypto` as `globalThis.crypto` (`Object.defineProperty`, since jsdom's empty `crypto` getter refuses a plain assignment) and `node:util`'s `TextEncoder`/`TextDecoder`, each guarded the same way as the `<dialog>` polyfill — a future jsdom that ships its own wins rather than being overwritten.
- **react-scripts sets `resetMocks: true`** — a mock implementation defined at module scope is wiped before every test. Stage them in `beforeEach` or they come back `undefined`.
- **In a git worktree under `.claude/worktrees/`, `npm test` discovers *nothing*** — not your new test, not any existing one — and exits 1 with "No tests found". CRA builds `testMatch` from `rootDir` and leaves a Windows path separator at the `.claude` segment (`…/budget\.claude/worktrees/…`), where a glob reads `\.` as an escaped literal, so the pattern cannot match the path it was generated from; `roots` is pinned (above) so there is no way to re-root out of it. Nothing is wrong with the checkout. Pass the one thing CRA does accept: `npx react-scripts test --watchAll=false --testMatch '**/*.test.js'`, or `'**/<name>.test.js'` for one file. Worth knowing before debugging a suite that is not actually running.
- A promise resolved in an effect needs `await act(async () => {})` before asserting, or its state update lands outside act.
- **CRA pins Jest's `roots` to `<rootDir>/src` and does not allow it to be overridden** (`createJestConfig.js` lists what it takes, and `roots` is not on it), so a test under `electron/` is never discovered — it does not fail, it silently does not exist. That is why `electronBooks.test.js`, `electronAssist.test.js` and `electronReceipts.test.js` test main-process code from `src/`. They drive the real modules against **real files in a real temp directory** (the atomicity relied on is the filesystem's own); `jest.resetModules()` before each `require` is required, since the module is a singleton over one file.
- A `<dt>` does not take its accessible name from its content, so `getByRole("term", { name })` finds nothing. Reach a figure through its term's text and `nextElementSibling`, scoped to the region.
- A `type="number"` input in jsdom refuses non-numeric text exactly as a browser does — but the only number fields left are the ages and the day count. **Money and rates are textboxes**, so `getByRole` wants `"textbox"`, `toHaveValue` takes a **string** (`"$12,500"`, or `""` for empty, never `null`), and a rejected figure can be tested with a word.
- React 17+ delegates `onFocus` through `focusin`: use `fireEvent.focusIn`, not `fireEvent.focus`.
- dnd-kit drags need `getBoundingClientRect` stubbed to give each row a band by its index (jsdom lays nothing out), and a **60ms wait after each drag**, or its 50ms click-swallowing listener eats the next test's first click.
- Deliver bridge answers inside `await act(async () => …)`. Left outside, the renders go to React's real scheduler and state a re-seed effect sets can still be pending when the next click lands. An empty `act()` afterwards does not help — it only flushes work scheduled inside it.
- A write that follows an `await` lands after the render its button appears in, so `waitFor` the stored record.
- **`remote` reads `false` for one tick while `AuthProvider`'s session check is still `checking`**, because both `BooksKeyContext` and `SyncContext` compute it off `AUTH_STATUS.SIGNED_IN`, which a session still being read back cannot be. `BooksKeyContext.test.js` and `SyncContext.test.js` both hit this: a `waitFor` on `hydrated`, or on "status is not `checking`", resolves on that first tick for the wrong reason — the gap, not the real session — and the assertion after it then races the actual fetch. Wait for a **terminal** state instead (`unlocked`/`setup`/`locked`, or `hydrated` **and** a `syncState` that is not the initial one), the same discipline `AuthContext.test.js` already needs around its own three-state `status`.

## Seeding

- Tests seed pre-migration JSON into `localStorage` before `renderHook` and use the real `AppProviders`, exercising migrations and provider order rather than mocking them. **That this works is the point of the migration's shape**: with no `AuthProvider` above them the storage scope is null, so a bare key is the real key and no network exists to mock.
- Seeding the `transactions` key — or the legacy `expenses` key, which still folds in — also fires the day-one assignment seed; to test spend with no funding, write an empty `assignments` key too.
- Any test that writes a transaction must seed an **account** first: the store refuses one without an `accountId`.
- **Tests that assert a whole stored record must list every field** — `payeeId`, `toAccountId` and `splits` on a transaction; `reconciledOn` on an account; `goalCents` on a budget. Several broke each time one was added, which is the point of asserting whole records.
- **Nothing mocks a hook.** Pages render through the real providers; that is what caught a column dropped from a table header and left in its body.

## The six tripwires — any change to the maths must keep these green

- **`dataModel.test.js`** — `expectBalanced` is the envelope identity written out, **including the `goalRows` and `assignedAheadCents` terms**; drop the first and every goal assignment reads as money vanishing, drop the second and so does every month funded ahead. Its **funding a month ahead** block asserts the half the store cannot see: next month's envelope funded, today's pool paying for it, no row or figure of the month on screen touched, a goal funded ahead drawing on the same pool, over-funding shown rather than refused, and a later month's withdrawal not reading as money free today. Its `transfers` block asserts the same identity in **all four quadrants** of the matrix, the only thing standing between a change to `budgetLegs` and a transfer that quietly creates or destroys money. Its splits block carries **`expectCoversLedger`**, the stronger one: it adds up the raw `amountCents` of every outflow in the seed — a reading with no notion of parts — so it catches a division and its whole drifting *together*, which `expectBalanced` (self-consistent by construction) would not. Its `moveBetweenBudgets` block asserts the move is **one write**, so the sum across the two rows is unchanged at every point a reader of storage could look.
- **`useRetirementProjection.test.js`** — a balance of `need` on the first day of retirement is a balance of zero on the last. The only thing holding the closed form and the year-by-year simulation to the same meaning.
- **`netWorthProjection.test.js`** — three: `expectIdentity` (each year's change in net worth is exactly income − consumption − tax − interest + growth + unfunded, from the unrounded `exact` figures), the reproduction of `projectRetirement` to the cent with only a retirement pot, and a pot of `need` ending at zero through `retirementOutlook`. Asserted again under every event kind, a purchase, a sale, and a down payment bigger than the cash.
- **`useSpendingReport.test.js`** — `netCents` equals every inflow less every outflow in the window, computed straight off the seed with no notion of income or refunds in it. `cashMoved` takes the off-budget account ids so it spells the transfer rule out for itself rather than reading `budgetLegs`: a tripwire that called the code under test would only assert the code agrees with itself.
- **`storage.test.js`**'s last test **reads `src/contexts/*.js` and fails if a store's key is missing from `STORE_KEYS`**. The only test in the suite that reads source, because nothing else can catch it — the app works perfectly until the user opens it somewhere else.
- **`amortization.test.js`** — asserted against loans computed by hand, never against the module's own output. For any principal, rate and term the contract schedule has exactly `termMonths` rows, Σ principal equals the original principal to the cent, Σ payment equals Σ principal + Σ interest, and the balance never rises; a zero rate is principal ÷ term; with extras Σ principal still equals the starting balance and the schedule is never longer than the baseline; a payment below the interest stops at the cap with `neverPaysOff`. The one thing holding `amortize` and the loan page's countdown, equity and what-if to the same meaning.

## Where a test goes

Three shapes, and the choice is not a matter of taste:

- **Props and spies**, where what is under test is a component's own contract — which patch a cell sends, what it does with a refusal. The rows arrive as a prop, so how they got there is somebody else's suite.
- **Through the real providers**, where the claim is that a figure *lands*. Anything crossing a store boundary, any cascade, any modal that writes twice.
- **The pure function, called directly**, where the arithmetic has a rule of its own and React would only be in the way.

A fourth shape is deliberately absent: **nothing mocks a hook.** `DashboardPage.test.js` renders the page through the real providers, and that is what caught a column dropped from the table header and left in its body.

## Props-and-spies suites

`TransactionRegister.test.js` stages `onChange` as a spy, since what it pins down is the cell contract: which patch a cell sends and what it does with the answer. `TransactionsPage.test.js` runs the same edits through the real providers, because an edit is only worth anything if it lands — that is where the direction flip, the refused flip, and the legacy-row correction are checked end to end.

- `SavingsGoalList.test.js` — the row's editing contract: which figure a cell sends, what it puts back and says when the store refuses one, and what a typed figure *means* against the one already in the cell (a leading "+" adds, a bare minus still states a negative). Its last block is the held-money reading, where the row's own job is stating the two piles apart. The store end, the delete cascade and the pool arithmetic are all in `dataModel.test.js`.
- `PaySchedulePanel.test.js` — which fields each cadence asks for and which patch each sends; the store end (the migration from a bare day count, a refused day of the month, the fields a switched-away-from cadence keeps) is in `useDashboard.test.js` with the rest of the paycheck wiring.
- `EmergencyFundPanel.test.js` — `PaySchedulePanel`'s split: which patch each field sends, which fields each answer asks for, and that a refused figure stays on screen with the message beside it.
- `AccountList.test.js` and `CategoryPlanner.test.js` — how the list is divided and what the row's editing contract is, not how the records got there. `CategoryPlanner.test.js` builds its sections with the real `toSections`, because the row reads `effectiveBucket` and a hand-built fixture could supply it differently from the fold the page uses.
- `BalanceHistoryPanel.test.js` — the grid rather than the store: the blank-versus-zero contract, where a typed month becomes an `amountCents` entry, the months around it stay blank ones that clear, and the figure carries forward without a record being invented for it. The store end, including the all-or-nothing window commit, is in `dataModel.test.js`.
- `PayeeField.test.js` — the control's contract: the keyboard, `aria-activedescendant`, Escape not reaching the dialog, and which of the two answers (`onCommit` / `onType`) it reports.
- `CardOfferList` and `CardValueList` — rows and spies, like `SavingsGoalList`; both are driven through `RewardsPage.test.js` rather than alone, since what is worth asserting is the figure the page's own stores produce.

## Pure-function suites

- `paySchedule.test.js` — the calendar arithmetic, and **every date in it is a real day in 2026 written out rather than derived from today**: the weekday is the whole point, so a fixture computed from `todayISO()` would test nothing about a Saturday.
- `rewards.test.js` — its **card offers** and **credits to use up** blocks drive `offerProgress` and `nextOfferWindow` with every date written out against a fixed today, and its **what a card earns** block does the same for the earn rates: that a multiplier and a percentage meet on one figure, that **the household's valuation is what settles which card wins** (asserted both ways round, since that is the claim the comparison rests on), that a card pays its best matching rate and nothing where it claims none, that earnings read the window, the splits, the refunds and the transfers exactly as an offer does, and that a fee year is the year the fee bought.
- `payeeSearch.test.js` — the ranking.
- `duplicates.test.js` — what counts as a second copy of a logged entry, with every date written out: the three-day window both ways and across a month end, that the payee only rules a match out (a different one, or a name not yet on file), that the category plays no part, a transfer matching only its own pair of accounts, and an undated record never matching. The form end — said live, the first Add held with nothing written, a changed entry asked afresh — is `AddModals.test.js`'s **warning about a transaction already in the books** block.
- `payeeDefaults.test.js` — a payee's remembered split: that the parts laid out add up to **any** total exactly (uneven ones, since an even total passes with any rounding), and that a part too small to be a share is not remembered at all. The form end — laid out against the total, following it until a part is touched, the "next time" boxes — is `AddModals.test.js`'s **what a payee opens the form on** block; the store end, including the merge adopting filing as one answer, is `dataModel.test.js`'s.
- `socialSecurity.test.js` — the claiming adjustment, and **the nine shares are written out rather than derived**, `paySchedule.test.js`'s rule: a fixture computed from the same three statutory rates the module uses would only assert that the code agrees with itself. The claim worth having beyond the table is the **bend at three years out** — the first thirty-six months before full retirement age cost 5/9 of a point each and the months beyond them 5/12, so a single straight rate would put 62 at about 73% instead of 70%. That the event it writes *lands*, and reaches the need, is `RetirementPage.test.js`'s.
- `assistant.test.js` — the resolution as the pure function it is, with the model's reply written out as an object and every date a real day (2026-10-08 is a Thursday).
- `reorder.test.js` (the subset rule) and `reordering.test.js` (the store end of a drag).
- `chartAxis.test.js` drives only the two functions in that module with a **rule** rather than a shape — `movingAverage`'s null head and `lineRuns`' break across a gap. Everything else there is asserted through the charts, where a tick or a stack is visible as a coordinate; these two matter for *where they refuse to answer*, and a null is invisible in a rendered path.
- `booksCrypto.test.js` — the round trip (wrap, unwrap, encrypt, decrypt) under both a password-derived and a recovery-code-derived KEK; a wrong password or recovery code fails closed rather than throwing; a **tampered** envelope (one byte flipped in `iv` or `ct`) fails the same way, which is GCM's tag doing its job rather than this module's; rewrapping MK under a new password leaves every document sealed under the old one still readable, since nothing about a document changes when only its wrap does; `encryptBytes`/`decryptBytes` round-trip a binary blob unchanged, the receipt path's own framing; and `isEncryptedDocument` says no to every real shape `STORE_KEYS` can hold, which is what lets hydrate tell a sealed row from a plaintext one on sight.

## Chart suites

`NetWorthChart.test.js` takes props directly — the one pure component worth testing alone — and asserts:

- no coordinate is `NaN`
- an all-zero file draws nothing rather than dividing by an empty domain
- a negative slice is drawn below the baseline, read off the path coordinates, since that is the only place the side is visible
- a decade thins the axis labels rather than printing 120
- focus opens the same read-out as hover
- the hit areas carry a **roving tabindex** — one tab stop, arrows between months — because ten years is 120 of them

`CashflowChart.test.js` is the same suite for the same reasons, plus the one thing that chart can get wrong on its own: a month whose refunds outweighed its spending must draw **above** the baseline, read off the paths against the zero line's own `y1`.

`PlanVsActualChart.test.js` is the third of that family and adds the two rules only it has: the threshold is **on the plot even when every month came in well under it** (read off the dashed line's `y1` against the hit areas' own top), and a month the books do not reach carries **no verdict** while the line still spans it.

`CashflowSankey.test.js` asks the diagram the same family's questions — no NaN, nothing drawn out of nothing, focus opens the read-out, one tab stop with arrows across every node. Its arithmetic (conservation, income always first, the negative sides, the folding) is `cashflowSankey.test.js`'s, the pure function called directly.

`NetWorthByAgeChart.test.js` is `NetWorthChart.test.js`' suite asked of the new chart, and `ScenarioCompareChart.test.js` the same for the comparison lines.

Its **what each card earns** block does the same for rates: the whole stored record from the form, a card's **whole table entered in one pass** and landing as one write, **one bad row refusing all of it** by name and leaving storage empty so the corrected retry cannot double the good rows, the comparison table naming the card to reach for, a valuation typed at the foot of the page changing which card that is, and the per-rate earnings read off the register. **Every query inside a form is scoped to its dialog** (`form(name)`, off `Dialog`'s `aria-label`), because the page holds four modals at once and two of them ask the same questions — and inside the rate form, scoped again to its row's group (`Rate 2`), because every row of it names every category.

## Infrastructure suites

- **`storage.test.js`** covers the namespacing — that two accounts on one browser cannot read each other's books, that sign-out takes an account's books out of the cache and leaves the unscoped ones alone, and that an empty `[]` is not "books to import". It stages a fake `window.__hbDesktop` and calls `resetStorageBackend()` to pick it up, which is the only reason that export exists — nothing in the app calls it, since the shell cannot change mid-session. Also covers `BOOKS_KEY_CACHE_KEY`: the cached key leaves with `clearScope` the same way the outbox does, and is **not** in `STORE_KEYS` — which the last test, the tripwire below, would otherwise catch as a store a context forgot to list, since `BooksKeyContext` persists it through `readKey`/`writeKey` directly and never through `useSyncedState`.
- **`useSyncedState.test.js`** is the old `useLocalStorage` suite plus the sync half: what the hook pushes, what it does with a change from another device, and that an unreadable remote document leaves the store alone rather than blanking it. It stages a `SyncContext.Provider` directly rather than standing up a real one.
- **`AuthContext.test.js`** mocks `../supabaseClient` and drives the provider and the gate. Its **signing in by email** block asserts `signInWithOtp`'s `options` **whole**, the discipline this suite keeps for a stored record and for the same reason: those options are the entire security content of the call, so `shouldCreateUser` going missing is exactly the kind of regression nothing else would show as a failure. The two halves worth not losing: an unknown address reports `{ ok: true }` **and** sets `pendingSignInEmail`, since a wording-only fix would leave the following screen distinguishable; and the shell's call carries no `emailRedirectTo` **key at all**, staged by assigning `window.__hbDesktop` the way `storage.test.js` does.
- **`BooksKeyContext.test.js`** mocks `../supabaseClient` the way `AuthContext.test.js` does (`resetMocks: true` means staging the implementation in `beforeEach`), and its `mountKey(expected)` helper takes **the terminal status the test is about** rather than waiting for "not `checking`" — the trap above, which would otherwise resolve on the inert first tick. Covers set-up minting and storing a key record and asserting **neither secret reaches the row**, unlock by password, a wrong password refused by a failed unwrap and nothing else, unlock by recovery code (including one retyped lowercase and without its hyphens), the cached key surviving a remount with no password asked again, a corrupt or wrong-`kid` cache falling to `locked` rather than crashing, `changePassword` writing **one** row and leaving a document sealed before it still readable, the concurrent-set-up race falling to `locked` when another device's row wins, and the provider going inert with no server configured. Its **key cache** block is the tripwire for a real bug: the cache must be written under the account's scope, so it asserts the *unscoped* slot is empty as well as that the scoped one is full — an unscoped write survives `clearScope` and leaves the master key for the next person to open the browser.
- **`BooksEncryptionPanel.test.js`** is props-and-spies in the sense that matters here: it pins what the panel does with whatever the key context reports, not the key itself. Both context objects (`SyncContext`, `BooksKeyContext`) are exported precisely so this suite can stage them through their real `Provider` and keep the "nothing mocks a hook" rule. Covers both halves of what the server can see being on screen, a refused password change surfaced rather than reported as success, the controls absent while merely `locked`, a regenerated recovery code shown once, and the panel rendering **nothing** with no key context or no `remote` above it — the shape every page suite renders it in, and the assertion that fails loudly if that optional read regresses.
- **`SyncContext.test.js`** — new, and the one that matters most of the three: **what reaches the wire is an envelope and never a document**. Also covers two flushes of the same document producing *different* ciphertext (a fresh IV every call) while still costing one write each rather than looping; a plaintext row arriving on hydrate being accepted as-is and then re-pushed sealed; an envelope that will not decrypt refusing the render instead of blanking a store; a realtime envelope landing decrypted in the store (delivered as a Broadcast notification naming the row, which the handler fetches — and our own write's echo, recognised by its IV, costing no fetch); and a flush with no key available queuing rather than sending. Hits the `remote`-for-one-tick trap above.
- **`receipts.test.js`** pins the signed-in upload path with a mocked `getSupabase` — it is the bucket's policy. Extended for encryption: an account-medium upload sends bytes that are not the file's own, a sealed receipt round-trips through `readReceipt`, an **unsealed** receipt (attached before encryption existed) still downloads and opens, and the `COMPUTER`/`BROWSER` media are byte-for-byte unchanged.
- **`electronBooks.test.js`, `electronAssist.test.js`, `electronReceipts.test.js`** test main-process code and live in `src/` anyway, the one placement in this suite that contradicts the rest; the Environment section above has the reason. `electronBooks.test.js` drives `electron/books.js` and pins down durability — the debounce pair, the launch-time backup taken once, the quarantined unreadable file, and that a refused write stays dirty. A mocked `fs` would only assert that the module calls `renameSync`. `electronAssist.test.js` uses `@jest-environment node` and a real HTTP server on a real loopback port standing in for Ollama; what is pinned is the wire — the schema sent as `format` at temperature zero, Ollama's own error passed back, a non-JSON reply refused, and every malformed request refused **before** anything is sent.

## Suites that deliberately do not exist

**`SplitParts` has no suite of its own on purpose**: it holds no rules, only the arithmetic both hosts already exercise. `AddModals.test.js` drives it through the entry form and `TransactionsPage.test.js` through the register and the editor, which is where the two contracts that matter actually live — nothing is written until the whole division checks out, and a refusal leaves the form on what was typed.
